# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`cc-outline` (command `cco`) is a terminal viewer that runs in a split pane next to Claude Code. It has six views: **Chat** (the session's turns rendered as Markdown, following live), **Changes** (git status plus diffs against `HEAD` with syntax highlighting, C# only so far) **Plan** (the plans Claude presented in plan mode, with status and a diff between versions) and **Sessions** (an overview of the project's sessions: time span, plans, changed files, prompts and the resume command) **Monitor** (response speed, wait and errors over the day, from all transcripts) and **Settings** (all options in one place, including `autoOpen`). It ships as an npm CLI (`cco`) plus a Claude Code plugin in `plugin/` (hooks and the `/cco:chat`, `/cco:git`, `/cco:plan`, `/cco:session`, `/cco:settings` and `/cco:monitor` commands). User-facing docs and key bindings are in `README.md`.

## Commands

```sh
npm run build        # tsup → dist/cli.js (single ESM bundle with shebang)
npm run dev          # tsup --watch
npm run typecheck    # tsc --noEmit (TypeScript 7)
npm test             # vitest run
npx vitest run test/git.test.ts            # one file
npx vitest run -t "breaks after slashes"   # one test by name
npm link             # expose `cco` globally; it runs dist/, so rebuild after changes
npm run demo         # re-record the README images in docs/ (headless run on demo/fixture.mjs; the GIF needs Chrome)
claude --plugin-dir ./plugin               # load the plugin (hooks + commands) for one session
claude plugin marketplace update cc-outline && claude plugin update cco@cc-outline   # refresh the installed plugin
```

CI (`.github/workflows/ci.yml`) runs typecheck, tests, build and `cco --version` on Linux, Windows and macOS with Node 22 (the minimum, Ink 7 needs it) and 24, for pushes to `main` and every pull request. Issue forms for bugs and feature requests are in `.github/ISSUE_TEMPLATE/`.

Releasing: `/cco-release [patch|minor|major|x.y.z]` (project skill in `.claude/skills/cco-release/`) does all of it and writes the release notes; `/cco-release --dry-run` only proposes the version and the notes. By hand: `npm version <version> --no-git-tag-version` on a `release/<version>` branch bumps `package.json` and the lockfile, and its `version` hook (`scripts/sync-version.mjs`) also `plugin/.claude-plugin/plugin.json` and `src/version.ts` (`test/version.test.ts` checks all four); merge that PR, then publish a GitHub release `v<version>` on `main`. `.github/workflows/publish.yml` then publishes to npm through Trusted Publishing (OIDC, no token; configured on npmjs.com for this repo and that file name, with provenance) after checking that the tag matches `package.json`; `prepublishOnly` runs typecheck, tests and build. Don't publish by hand as well: npm refuses a version twice.

The plugin is installed from this repo, which is its own marketplace (`.claude-plugin/marketplace.json`). Claude Code runs a cached copy, so changes under `plugin/` need the update command above. The plugin calls `cco` by name, so `npm link` is required for the hooks and commands to work. A running viewer pane keeps the code it was started with: after a rebuild, close it with `q` and reopen it. Plugin changes (hooks, commands) only load when Claude Code restarts.

## Architecture

**Data flow.** Claude Code writes every session as JSONL to `~/.claude/projects/<slug>/<session-id>.jsonl`. The slug is the cwd with every non-alphanumeric character replaced by `-`, see `projectSlug` in `src/transcript/locate.ts`. The viewer never talks to Claude Code directly. It tails that file (`FileTail` in `src/transcript/tail.ts`, reading from a byte offset) and feeds chunks to `TranscriptParser` (`src/transcript/parse.ts`). The parser groups entries into turns (a real user prompt plus all assistant blocks until the next prompt) and buffers incomplete trailing lines.

**Transcript format quirks** (handled in `parse.ts`):
- One assistant message is split across several lines that share `message.id`, one line per content block.
- `user` entries also carry tool results, `isMeta` reminders, interrupt markers and `<local-command…>` output. Only real prompts start a turn; slash commands are shown as `/name args`. Some slash commands (`/rename`, `/color`) are not `user` entries but `system` entries with `subtype: "local_command"` and `content` `<command-name>…`, followed by one with `<local-command-stdout>`; `localCommandPrompt` makes them a finished turn. `/resume` is not recorded at all.
- A `!` command is written only after it ended, all at once: an `isMeta` `<local-command-caveat>`, a `user` entry `<bash-input>cmd</bash-input>` (the prompt `! cmd`) and one `<bash-stdout>…</bash-stdout><bash-stderr>…</bash-stderr>` (not a prompt: `shellOutput` makes it the turn's answer as a code block and ends the turn). Both are HTML-escaped (`&lt;`, `&amp;`) and the output keeps color codes. `isCommand()` tells `/` and `!` prompts apart from questions to Claude.
- `/compact` is written twice: the `/compact` prompt as typed, then, after the `compact_boundary` and the summary (a `user` entry with `isCompactSummary`, not a prompt), as `<command-name>/compact`; the parser merges them into one turn. The summary becomes a `{ kind: "compact" }` block with the boundary's `compactMetadata` (`CompactInfo`), without the lines meant for Claude (`compactSummaryText`: the opening sentence up to "Summary:", the closing "If you need specific details…" / "Continue the conversation…"): the `/compact` turn's answer, the first entry of a transcript read without its predecessor, or, for an automatic compaction mid-turn (no prompt), a turn of its own (`compacted`, `⟳` in the list) that the work after it belongs to. `answerLines` renders it like a recap, with a blue bar (`compactLines`); `c` copies it. Claude Code can go on in a new session id (seen when `/compact` sent the session to the background: `sessionKind: "bg"`, run by the daemon, whose hooks have another `CLAUDE_PID`): the old transcript ends with `{ type: "continued-in", continuedInSessionId }`, and the new one, in the same folder, starts with copies of the last entries (same uuids). `TranscriptParser.continuedIn` records it, and the entry becomes a turn of its own (`continuation`, id `continued-<id>`, done): the ids, the last `compact_boundary`'s `compactMetadata` (trigger, pre/post tokens, duration) and whether an `informational` "Backgrounding…" entry came since the last prompt. Claude's answers after it belong to that turn; `ChatView` marks it `⤷` and shows the details in its header (`continuationDetails`); Sessions and `typedInClaude` leave it out like notifications. A transcript read without its predecessor starts with such a turn too (`start`, `Continued from an earlier session`); `useTranscript` then reads on in that file with the same parser (`dedupe` skips known uuids, `nextFile()` drops a partial line), stamps turns and agents with their `transcript` (images, subagents) and returns the current `file`, which `App` uses as its path, and `continuedFrom`. `App` writes the new transcript into its process's `claude-<pid>.json` (`continueSession`), so the old session's end does not close the viewer and the path change keeps the turns, but only while that file still names `continuedFrom`: comparing `file` with the resolved path instead wrote the old session back after `/resume` (for one render `file` is still the previous session's), and the chat flipped between the two sessions. The new transcript does not name the old one (only the summary's prose does), so opening it (after `/resume`) finds its `predecessors` (`src/transcript/continuation.ts`): if its first entry with a uuid is a `compact_boundary`, the transcript in the same folder whose end has a `continued-in` to it, repeated back along the chain; `useTranscript` reads those first. Without them the first copied answer has no prompt and becomes that `start` continuation turn instead of `(session start)`. The Sessions view shows such a chain as one session (`mergeContinued`, with `continues` naming the earlier ids and the later id for `--resume`), merged before the `hasWork` filter; the trash moves and restores all its parts.
- A recap (`system` entry, `subtype: "away_summary"`, text in `content` ending in "(disable recaps in /config)") becomes a `{ kind: "recap" }` block of the last turn; `answerLines` in `ChatView.tsx` renders the Markdown in runs between recaps and each recap with a yellow bar. It is not part of `turnMarkdown` (copy with `c`).
- Sidechain entries (subagents) are skipped in the main transcript. A subagent has its own transcript, `<session-id>/subagents/agent-<agentId>.jsonl`, of sidechain entries only, next to `agent-<agentId>.meta.json` (`toolUseId`, `agentType`, `description`); `new TranscriptParser({ sidechains: true })` reads it like a main one (`src/transcript/subagents.ts`, `useSubagent`).
- Subagents are `Agent` (formerly `Task`) tool calls: `input.description`, `subagent_type`, `model`, `prompt`, `run_in_background`. The parser turns each into an `AgentRun` (`parser.agents`, and a `{ kind: "agent" }` block in its turn) and updates it in place: the tool result's `toolUseResult` carries `agentId` and, for a background agent, `status: "async_launched"`; a foreground agent's result is its report (`totalTokens`, `totalToolUseCount`, `totalDurationMs`). A background agent ends with a `<task-notification>` (`tool-use-id`, `status`, `summary`, `result`, `usage`), sent as a `user` entry with `origin.kind: "task-notification"` when Claude is idle or as a `queued_command` with `commandMode: "task-notification"` mid-turn. Background Bash commands send the same. Notifications are not prompts: they become turns with `notification` set and `prompt` = summary, so Claude's reaction has a place, and the Sessions view leaves them out of the prompts.
- Pasted images are `image` content blocks in the prompt (also in `queued_command` prompts). A prompt of images only has no text, so it gets `[Image]` / `[3 images]` as its prompt (`imagesLabel`); otherwise it would start no turn.
- Attachments of a prompt (`Turn.attachments`): its `image` blocks, then `attachment` entries that directly follow it: `inlined_image_paths` (the images' copies in `~/.claude/uploads`, in paste order), `file`/`directory` (@-mentions) and `selected_lines_in_ide`/`_diff`. Any `user`, `assistant` or `system` entry ends that window (`takesAttachments`): after `/compact`, Claude Code writes `file` attachments for files it had read, right after the "Compacted" local command output, and those are not the user's. `o` in the chat opens images via `turnImageFiles` (`src/images.ts`): the upload copy if it exists, else the base64 block of the prompt's transcript line written to `<tmp>/cco-images/`.
- Prompts typed while Claude is working are not stored as `user` entries. When Claude takes them in mid-turn, they appear as `type: "attachment"` with `attachment.type: "queued_command"` and `attachment.prompt`; `queue-operation` lines only record the queueing. They start their own turn with `queued: true`, shown as `↳` in the list.
- A turn is `done` after an assistant line with `message.stop_reason` `end_turn`/`stop_sequence` (a later `tool_use` line resets it), a `system` entry with `subtype: "turn_duration"` or `local_command`, or `<local-command-stdout>` output. `[Request interrupted by user]` and `[Request interrupted by user for tool use]` arrive as `user` text entries and set `interrupted` (`user`/`tool`) on the last turn. The chat shows a `Spinner` for the last turn while it is neither, but only when the viewer follows the running session (`liveSession`, not with `--session`); the demo fixture's answers therefore carry `stop_reason: "end_turn"`.
- The `ExitPlanMode` line is only written once the user decided. For the plan being written, `plan_mode` attachments (`attachment.planFilePath`, not for subagents) start plan mode and `plan_mode_exit` ends it (`TranscriptParser.planMode`); the Plan view shows that file as a `draft` while it is newer than plan mode's start and differs from the plan presented last (`draftPlan` in `PlanView.tsx`).
- A tool call is written to the transcript only once the tool has finished (with its `tool_result` right after), so a running command or an unanswered `AskUserQuestion` is not in the file yet. Each `tool_result` entry carries a structured `toolUseResult` that differs per tool (Bash: `stdout`/`stderr`/`interrupted`; Read: `file.{startLine,numLines,totalLines}`; Edit/Write: `structuredPatch`; Grep/Glob: counts and `filenames`; AskUserQuestion: `answers` question → label or typed text, `annotations`). `toolOutcome` (`src/transcript/tools.ts`) reduces it to what the chat shows when the result arrives, so no file contents are kept; `toolMarkdown` renders a call at the `showTools` level (`off`/`compact`/`full`), questions at every level.
- Plans are `ExitPlanMode` tool calls (`input.plan`). The user's decision is the matching `tool_result` in a later `user` entry: `is_error: false` means approved, `is_error: true` rejected, with optional feedback after "the user said:". `TranscriptParser.plans` collects them; Claude Code also writes plans to `~/.claude/plans/`, but with random names and no project, so the transcript is the source.

**Hooks and state files.** `cco hook` (`src/hook.ts`) handles `SessionStart`, `UserPromptSubmit` and `SessionEnd` and writes per-project state files to `~/.claude/cco/<slug>*.json`. All of them are written atomically via rename (`writeJson` in `locate.ts`):
- `<slug>.claude-<pid>.json`: the session of one Claude Code process (`CLAUDE_PID`, which Claude Code passes to hooks and commands; `claudePidFromEnv`). Same shape as `<slug>.json`, and `ended: true` on `SessionEnd` (not `clear`) of that process's session. A viewer started with `--claude-pid` (which `cco open` passes) follows only this file and also exits when the pid is gone. Stale files of dead pids are removed on `SessionStart`.
- `<slug>.json`: the project's latest active session, for viewers without a pid (`cco watch` by hand). `ended: true` is set on `SessionEnd`, except when the reason is `clear`, and only if that session is still the active one.
- `<slug>.viewer-<claudePid>.json` (`<slug>.viewer.json` without a pid): pid and current view of the running viewer. `cco open` checks the one of its own Claude Code process and reuses a live viewer instead of opening a second pane. `restore.json` is only rewritten by a session with its own viewer or when no viewer runs in the project, and `SessionStart` reopens only when none runs.
- `<slug>.restore.json`: whether a viewer was running at `SessionEnd`, and with which view. On `SessionStart` with source `startup` or `resume`, the hook opens the viewer as the `autoOpen` setting says (`remember`: only if this says it was open; `always`: also without it, in the chat; `never`) with `keepFocus`, which sends a `move-focus left` to wt or passes `-d` to tmux. The hook must not print to stdout, because SessionStart output is added to Claude's context. Claude Code writes a prompt to the transcript only after the `UserPromptSubmit` hooks ran, so `cco hook` must start fast: `cli.ts` loads the viewer (`src/watch.ts`: Ink, React, the renderers) with a dynamic `import()` for `cco watch` only, and tsup splits it into its own chunk. Code shared with it lands in another chunk, so `open.ts` starts `dist/cli.js` by name (`CLI`), not its own `import.meta.url`.
- `<slug>.positions.json`: per list (`chat`, `git`, `plan`, `sessions`) the selected entry, whether it followed the newest, and a scroll position per key (turn id, path, `path#file`, plan id, `id#diff`, session id), at most 500 per list (`src/positions.ts`). Views use `usePositions()`, whose `scroll(key, …)` replaces `useScroll`; switching entries must not call `scroll.set(0)`, that would reset the entry being left. Chat and Plan restore the selection once their entries are loaded and store nothing before that. The chat list's position is one per project: a stored selection the shown session does not have (e.g. the new session `/resume` starts in, before it switches) is kept while that session is only followed (`unrestored` in `ChatView`), so the resumed session gets it back. Its reset effect on `path` runs before the follow effect (deps include `path`): a session continued from other transcripts arrives with all its turns in the same render as the path change, and `last` does not change then.
- `<slug>.views.json`: per session id (at most 500, `src/sessionViews.ts`) the view it was shown in last and the placement chosen for it with `p` (`{ view, placement }`; the first format stored the view as a plain string and is still read). `resolvePlacement` gives the session's placement, else the `placement` setting. With the `rememberView` setting, `App` records it and switches to it when the followed session changes (`/resume`), `cco watch` without `--view` starts in it, and the `SessionStart` hook reopens in it before falling back to `restore.json`'s view. An explicit `--view` (the `/cco:…` commands) wins.
- `<slug>.control-<claudePid>.json` (`<slug>.control.json`): view-switch requests from `cco open` to the running viewer.
- `<slug>.favorites.json`: marks of all five lists (`src/favorites.ts`): `turns` (prompt uuids), `files` (paths), `plans` (tool call ids), `sessions` (session ids) and `days` (Monitor, `YYYY-MM-DD`). Kept per project, not per session: `--continue`/`/resume` start a new session id but copy the turns with their uuids. The first format (one list per session id) is merged into `turns` on read. Views use it through `useFavorites()`; `markKeys()`/`markFooter()`/`Star` in `layout.tsx` keep Space and Shift+←/→ the same everywhere.

**Monitor** (`src/monitor/`, `MonitorView.tsx`): `ResponseReader` reads every transcript (and `<session>/subagents/*.jsonl`) incrementally and keeps one small `Response` per API response: `start` = the timestamp of the `user` entry before it (prompt or tool result; main and sidechain tracked apart), `first`/`end` = its first and last line with that `message.id`, `model`, `output_tokens`. `<synthetic>` messages are skipped; `isApiErrorMessage` entries are the only errors transcripts have. Speed = tokens / (end − start), wait = first − start; responses under 0.5 s, over 10 min or under 50 tokens are counted but not timed. `dayBuckets`/`typicalBuckets` take medians per stretch (local time), `barChart` draws them in eighths. The overall index (`scoreOf`, `dayScore`) is the geometric mean of speed / usual and usual / wait × 100; the day's is weighted by each stretch's `measured` responses. `Enter` swaps the chart for `responseTable` (one row per response, index against its stretch's usual values), which keeps its scroll position under `<day>#table`. `IncrementalFile` (`src/transcript/incremental.ts`) is the byte-offset line reader shared with `SessionReader`.

Settings are global rather than per project: `~/.claude/cco/settings.json` (`src/settings.ts`), with defaults in `DEFAULT_SETTINGS`; `readSettings()` falls back to the default for values of the wrong type or, for `autoOpen`, unknown ones. Views use them through `useSetting()`, which writes on every change; `updateSettings()` notifies `subscribeSettings()` listeners and `useSetting` reads a cached copy through `useSyncExternalStore`, so a change in the Settings view (or `t` in Chat) shows in every view at once. `SettingsView.tsx` builds its list and details from `SETTING_ROWS`; a new setting needs an entry there (a test checks that every key of `DEFAULT_SETTINGS` has one). The Settings view's Reset entries (`RESET_ACTIONS`) reset all settings, or delete the project's data files (`src/projectData.ts`: favorites, positions, views, restore; not the hook state). `App.resetProjectData` pauses position writes (`suspendPositionWrites`, since unmounting views would save theirs again), deletes the files and remounts all views through a `Fragment` key. `confirmQuit` is read in `App`, `marquee` in `EntryText`, `rememberPositions` in `usePositions` (off: neither read nor written). The view settings (`viewChat` … `viewMonitor`, `VIEW_SETTINGS`) hide tabs: `Tabs` skips a hidden view unless it is the open one, `App` ignores its number key, and `shownView` replaces a remembered view that is hidden (App start, `/resume`, the SessionStart hook); an explicit `--view` still opens it. Settings has no such setting, and `isLastView` keeps one other view shown.

Focus indication (`src/tui/focus.ts`): the viewer enables terminal focus reporting (DECSET 1004). Ink passes the reports to `useInput` as `"[I"` and `"[O"`, with the ESC stripped and no key flags set, so no view binding reacts to them. `FocusContext` feeds `Screen` (top bar, footer) and `List` (selection style). A pane opened with `keepFocus` starts with `--unfocused`, because the terminal sends no initial report. Windows Terminal 1.12 sends no reports at all, so `focusFromInput` also counts any key or click as focus in, and `App` passes the time of the last prompt typed after the viewer started (`typedInClaude`) as focus out.

The viewer (`src/tui/useViewerControl.ts`) only reacts to changes that happen after it started. It exits when the session ends, after a 1.5 s grace period. Without hooks it falls back to the newest transcript that contains messages; Claude Code also creates tiny bookkeeping `.jsonl` files that must be ignored.

**TUI** (Ink 7 + React 19, `src/tui/`):
- `App.tsx` reads the transcript once (`useTranscript`) for the chat and plan views and keeps all views mounted (hidden with `display="none"`) so the chat keeps following while the git view is shown. Views use `useInput(..., { isActive })`.
- `SessionsView.tsx` reads the transcripts of all projects (or, with the `allProjects` setting off, of this one) through `SessionIndex` (`src/transcript/sessions.ts`) only while it is visible, every 3 s; the first scan reports partial results. `SessionReader` drops each turn's blocks right after taking the changed files from them, so ~750 MB of transcripts stay at ~70 MB heap. One `SessionReader` per file keeps a byte offset and a `TranscriptParser`, so a rescan only parses what was appended. It adds what the parser ignores: the `/rename` title (`custom-title` entries), `gitBranch`, the time span and the files of `Edit`/`Write`/`MultiEdit`/`NotebookEdit` calls. Sessions with only slash commands and no changes are left out.
- `Enter` starts a session, after a confirmation, with `resumeInNewTab` (`src/open.ts`): `wt -w 0 new-tab -d <cwd> cmd /k claude --resume <id>` (cmd finds both claude.exe and an npm .cmd shim and keeps the tab open), or `tmux new-window` with `exec $SHELL` afterwards. Active and running sessions are refused.
- Deleting (`src/transcript/trash.ts`) works on the session's own project folder (from `SessionSummary.path`, not the viewer's cwd) and moves its parts (`projects/<slug>/<id>.jsonl`, `projects/<slug>/<id>/`, `file-history/<id>/`, `session-env/<id>/`) to `~/.claude/cco/trash/<slug>/<id>/` under their path relative to `~/.claude`, with a `manifest.json` (items, deletion time, the `SessionSummary` for display). Restore moves them back and refuses if a path exists again; purge removes the trash folder and the mark. The active session and sessions with a live pid in `~/.claude/sessions/<pid>.json` are refused. `ConfirmDialog` (on the shared `Dialog` frame in `layout.tsx`) asks first (Enter yes, Esc no); while it is open, `App` ignores its own keys (`onModal`).
- Mouse (`src/tui/mouse.ts`, setting `mouse`): `App` turns on reporting (DECSET 1000 + 1006, SGR); Ink hands each report to `useInput` without the ESC (`"[<0;12;5M"`), which no key binding matches. `useMouse()` parses them for the view whose `MouseContext` (set by `App`: shown, no dialog, setting on) is true. `Screen` puts the list and preview into `AreaContext` (their cells on the terminal), so `List` (`onPick`: click selects, wheel moves) and `Preview` (`onWheel`; a click on a URL opens it via `linkAt` in `links.ts`, which joins URLs wrapped over full lines) map positions themselves.
- List order: Chat, Plan, Sessions (and trash) and Monitor keep their data in its natural order (oldest first; Monitor days newest first). The `*Order` settings only mirror the display: `List` with `reversed` renders bottom-up and maps `onPick` back, `orderedNav` swaps ←/→ and first/last for `handleNavigation`, `orderedDir` flips the Shift+←/→ direction for `nextMarked`. Follow logic, positions and marks stay on the natural index.
- `layout.tsx` holds the shared pieces: the `Screen` frame, the `List`, `useScroll`, `handleNavigation`, `previewHeader`, `Marquee`/`EntryText` (the selected list entry scrolls, at most `MARQUEE_MAX_SCROLL` = 250 columns, then starts over) and `wrapPath`. All views share the same navigation: `←→` switch item, `↑↓` scroll.
- The top bar status shows counts and positions only. Whether an option is on (follow, tools, wrap, all projects, …) is shown by the help line, which highlights `FooterItem`s with `on`; do not repeat it in the status. `Screen` adds the version at the right end, but only if tabs and status leave room for it (measured with `measureElement` after each render), so it never cuts the status.
- Terminal title (`src/tui/title.ts`): `App` sets it with OSC 0 to the session title, else the project folder. The title comes from `TranscriptParser.title`: the last `custom-title` entry (`/rename`) over the last `ai-title` one (Claude Code's generated title); Claude Code repeats both entries throughout the transcript. The OSC write is control-only, so `FrameBuffer` passes it through and redraws the next frame in full.
- `Preview.tsx` renders a sticky `header` (prompt or file path, capped by `fitHeader`) above the scrolled lines. Like the list, it turns the first/last row into a `▲`/`▼ N more lines` indicator when lines are hidden (`previewWindow`); the row covers the line at `scroll`, so jumps to a line (hunks) scroll to one line before it. `spinner={{ line, active }}` replaces the first character of one line with a `Spinner` while it is visible ("Claude is working…"), so the pre-rendered lines stay memoized.
- All content is pre-rendered into ANSI strings that are already wrapped to the preview width, then sliced by scroll offset. Ink does no wrapping of its own here (`wrap="truncate"`).
- Double buffering (`src/tui/frameBuffer.ts`): Ink redraws every frame in full, and on Windows it clears the whole screen first whenever the output fills the terminal (`isWindowsConsole` in `ink.js`), which `Screen` always does; under load the terminal shows the empty screen in between. `cli.ts` hands Ink `frameBufferedStdout(process.stdout)`, a `Proxy` whose `write` goes through `FrameBuffer`: it strips Ink's frame prefix (`clearTerminal` or `eraseLines`), diffs the lines against the screen last written and writes only changed ones with absolute cursor positions (`ESC[K` only after lines narrower than the terminal, pending wrap), as one write in synchronized output (Ink's own separate `?2026h/l` writes are dropped). Control-only writes (alternate screen, cursor, focus/mouse reporting) pass through and, like `resize`, make the next frame a full redraw, which clears the screen and the scrollback (`2J` `3J`: Windows Terminal moves what `2J` erases into its scrollback, and the mouse wheel then scrolls the whole pane to old frames). Without a known prefix, a write counts as a frame only if it does not start with a cursor or erase sequence (the first frame starts with text or a colour); anything else passes through. An Ink update that changes the prefixes must be checked against `test/frameBuffer.test.ts`. `CCO_FRAME_BUFFER=0` turns it off.

**Rendering.**
- `src/render/markdown.ts` uses `marked` with `marked-terminal`, plus two fixes:
  - A `text` renderer override, because marked ≥13 hands list items nested inline tokens that marked-terminal prints raw.
  - A wrapper that indents the continuation lines of list items.
- `src/render/diff.ts` highlights each hunk side as one text, so multi-line comments are colored correctly, and then maps the lines back. Its truecolor theme applies styles per line (`style()`), because highlighted output is split into lines afterwards. Add languages via the `LANGUAGES` map.

**Git** (`src/git/git.ts`): uses porcelain v1 `-z` plus `numstat`. It diffs against `HEAD`, or against git's empty tree in repos without commits. Untracked files get a synthetic all-added hunk and are counted manually.

**Opening panes** (`src/open.ts`): `openPane` places the viewer as `right` (`wt -w 0 split-pane -V`, `tmux split-window -h`), `left` (the same plus `; swap-pane left`, because `split-pane` only opens right or below; tmux `-b`) or `window` (`wt -w cco-<claudePid> new-tab`, one named window per Claude Code process; `tmux new-window`). A Windows Terminal window keeps the focus: `move-focus` works only within a window. Don't spawn `wt` with `windowsHide` for a window: Windows Terminal applies the hidden start to the new window, which then exists but never shows. `p` in the viewer (`PlacementDialog`) saves the choice for the session and calls `moveViewer`, which starts `cco open --placement … --after-pid <viewer pid>` detached and quits; that waits until the old viewer has gone, so its pane or window has closed and `-w 0` means Claude Code's window again, then opens with `replace` (no reuse of the running viewer). The terminal is Windows Terminal or tmux (`detectTerminal`: `TMUX`, else `WT_SESSION` or `WT_PROFILE_ID`; `WT_SESSION` alone is not reliable, Claude Code can lose it when it restarts itself). Without `WT_SESSION` there is no tab to dock to: `-w 0` (and `-w last`, at least in Windows Terminal 1.12) makes wt create a new window, which `windowsHide` keeps invisible while the viewer runs in it, so `cco open` kept reusing an invisible viewer. That happens after Claude Code restarted itself and for sessions run by the Claude Code daemon (`claude.exe daemon run` → `--bg-pty-host` → the session's `claude.exe`, whose `CLAUDE_PID` is not below any WindowsTerminal process; the tab shows a client process). `openPane` then opens a `window` placement instead (`tabless`) and says so. It launches `process.execPath dist/cli.js` directly, because Windows Terminal cannot run npm's `.cmd` shims by bare name.

## Gotchas

- The viewer inherits the environment of the Claude Code it was opened from, including `CLAUDE_CODE_CHILD_SESSION=1`. A Claude Code started from the viewer with that marker thinks it is a child session and saves no transcript, so `resumeInNewTab` strips the session-bound variables (`independentEnv` in `src/open.ts`).
- `CLAUDE_CONFIG_DIR` may be set to an empty string. Use `||`, not `??`, when falling back to `~/.claude`.
- chokidar does not notice files created later if their directory does not exist yet; `watchFile` creates the directory first. On Windows it uses polling. `FileTail` also stats the file every second so it catches a transcript that does not exist yet.
- On this Windows machine, the Bash tool mangles backslashes in heredocs and inline scripts (`\\`, `\u001b`, `\n`). Write files containing escape sequences with the Write/Edit tools.
- TUI changes can be checked headlessly: render `App` from a tsup build into a `PassThrough` stdout with `isTTY = true` and `debug: true`, write key sequences to a fake stdin (e.g. `\u001b[C` for →), and inspect the output with ANSI codes stripped.
