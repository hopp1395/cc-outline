# Transcript format

How Claude Code writes a session and how `TranscriptParser` reads it.

**Data flow.** Claude Code writes every session as JSONL to `~/.claude/projects/<slug>/<session-id>.jsonl`. The slug is the cwd with every non-alphanumeric character replaced by `-`, see `projectSlug` in `src/transcript/locate.ts`. The viewer never talks to Claude Code directly. It tails that file (`FileTail` in `src/transcript/tail.ts`, reading from a byte offset) and feeds chunks to `TranscriptParser` (`src/transcript/parse.ts`). The parser groups entries into turns (a real user prompt plus all assistant blocks until the next prompt) and buffers incomplete trailing lines.

**Transcript format quirks** (handled in `parse.ts`):
- One assistant message is split across several lines that share `message.id`, one line per content block.
- `user` entries also carry tool results, `isMeta` reminders, interrupt markers and `<local-command…>` output. Only real prompts start a turn; slash commands are shown as `/name args`. Some slash commands (`/rename`, `/color`) are not `user` entries but `system` entries with `subtype: "local_command"` and `content` `<command-name>…`, followed by one with `<local-command-stdout>`; `localCommandPrompt` makes them a finished turn. `/resume` is not recorded at all, nor is `/btw` (side question): an `immediate` local-jsx command whose question and answer live in memory only (`session.btwHistory`, `display: "skip"`), so they are in neither the transcript nor `history.jsonl`, and no hook sees them; only `btwUseCount` in `.claude.json` counts them.
- A `!` command is written only after it ended, all at once: an `isMeta` `<local-command-caveat>`, a `user` entry `<bash-input>cmd</bash-input>` (the prompt `! cmd`) and one `<bash-stdout>…</bash-stdout><bash-stderr>…</bash-stderr>` (not a prompt: `shellOutput` makes it the turn's answer as a code block and ends the turn). Both are HTML-escaped (`&lt;`, `&amp;`) and the output keeps color codes. `isCommand()` tells `/` and `!` prompts apart from questions to Claude.
- `/compact` is written twice: the `/compact` prompt as typed, then, after the `compact_boundary` and the summary (a `user` entry with `isCompactSummary`, not a prompt), as `<command-name>/compact`; the parser merges them into one turn. The summary becomes a `{ kind: "compact" }` block with the boundary's `compactMetadata` (`CompactInfo`), without the lines meant for Claude (`compactSummaryText`: the opening sentence up to "Summary:", the closing "If you need specific details…" / "Continue the conversation…"): the `/compact` turn's answer, the first entry of a transcript read without its predecessor, or, for an automatic compaction mid-turn (no prompt), a turn of its own (`compacted`, `⟳` in the list) that the work after it belongs to. `answerLines` renders it under a heading with those numbers (`compactLines`), without the recap's bar, since it is usually the whole answer; `c` copies it. Claude Code can go on in a new session id (seen when `/compact` sent the session to the background: `sessionKind: "bg"`, run by the daemon, whose hooks have another `CLAUDE_PID`): the old transcript ends with `{ type: "continued-in", continuedInSessionId }`, and the new one, in the same folder, starts with copies of the last entries (same uuids). `TranscriptParser.continuedIn` records it, and the entry becomes a turn of its own (`continuation`, id `continued-<id>`, done): the ids, the last `compact_boundary`'s `compactMetadata` (trigger, pre/post tokens, duration) and whether an `informational` "Backgrounding…" entry came since the last prompt. Claude's answers after it belong to that turn; `ChatView` marks it `⤷` and shows the details in its header (`continuationDetails`); Sessions and `typedInClaude` leave it out like notifications. A transcript read without its predecessor starts with such a turn too (`start`, `Continued from an earlier session`); `useTranscript` then reads on in that file with the same parser (`dedupe` skips known uuids, `nextFile()` drops a partial line), stamps turns and agents with their `transcript` (images, subagents) and returns the current `file`, which `App` uses as its path, and `continuedFrom`. `App` writes the new transcript into its process's `claude-<pid>.json` (`continueSession`), so the old session's end does not close the viewer and the path change keeps the turns, but only while that file still names `continuedFrom`: comparing `file` with the resolved path instead wrote the old session back after `/resume` (for one render `file` is still the previous session's), and the chat flipped between the two sessions. The new transcript does not name the old one (only the summary's prose does), so opening it (after `/resume`) finds its `predecessors` (`src/transcript/continuation.ts`): if its first entry with a uuid is a `compact_boundary`, the transcript in the same folder whose end has a `continued-in` to it, repeated back along the chain; `useTranscript` reads those first. Without them the first copied answer has no prompt and becomes that `start` continuation turn instead of `(session start)`. The Sessions view shows such a chain as one session (`mergeContinued`, with `continues` naming the earlier ids and the later id for `--resume`), merged before the `hasWork` filter; the trash moves and restores all its parts.
- A recap (`system` entry, `subtype: "away_summary"`, text in `content` ending in "(disable recaps in /config)") becomes a `{ kind: "recap" }` block of the last turn; `answerLines` in `ChatView.tsx` renders the Markdown in runs between recaps and each recap with a yellow bar. It is not part of `turnMarkdown` (copy with `c`).
- Sidechain entries (subagents) are skipped in the main transcript. A subagent has its own transcript, `<session-id>/subagents/agent-<agentId>.jsonl`, of sidechain entries only, next to `agent-<agentId>.meta.json` (`toolUseId`, `agentType`, `description`); `new TranscriptParser({ sidechains: true })` reads it like a main one (`src/transcript/subagents.ts`, `useSubagent`).
- Subagents are `Agent` (formerly `Task`) tool calls: `input.description`, `subagent_type`, `model`, `prompt`, `run_in_background`. The parser turns each into an `AgentRun` (`parser.agents`, and a `{ kind: "agent" }` block in its turn) and updates it in place: the tool result's `toolUseResult` carries `agentId` and, for a background agent, `status: "async_launched"`; a foreground agent's result is its report (`totalTokens`, `totalToolUseCount`, `totalDurationMs`). A background agent ends with a `<task-notification>` (`tool-use-id`, `status`, `summary`, `result`, `usage`), sent as a `user` entry with `origin.kind: "task-notification"` when Claude is idle or as a `queued_command` with `commandMode: "task-notification"` mid-turn. Background Bash commands send the same. Notifications are not prompts: they become turns with `notification` set and `prompt` = summary, so Claude's reaction has a place, and the Sessions view leaves them out of the prompts. Since Claude Code 2.1.283 a background agent first hands back its report as a message from a "peer" (`SubagentHandback`): a `user` entry with `isMeta: true` and `origin: { kind: "peer", from: <agentId>, senderTaskId, body, handback: true }` ("Another Claude session sent a message: <agent-message from=…>"), or mid-turn a `queued_command` attachment with that `origin`; `body` is a preamble up to "The report follows:" and the report, every line indented by two spaces. Its `<task-notification>` then only says `This agent's report was delivered to you as a message…`, which `taskNotification` drops. `addPeerMessage` makes the message a turn like a notification (`notification.kind` `handback`, or `message` for another session writing; prompt `Agent "…" reported back` / `Message from …`), so Claude's reaction to the report lands there and not in the turn before (isMeta entries start none), and the report (`peerText`: preamble and indentation removed, JSON as a code block) becomes the agent's `result`. `answerLines` shows it above the reaction with a magenta bar (`peerLines`); the list marks the turn with a magenta `↩`.
- Dynamic workflows (seen with Claude Code 2.1.300; shapes from session `fc0e63aa`, rebuilt with made-up contents in `test/helpers/workflow.ts`) are `Workflow` tool calls whose `input.script` is the script (a re-run: `{ scriptPath, resumeFromRunId }`); name, description and phases are only in its `export const meta = { … }` literal, which `workflowMeta` reads with patterns. The result returns at once: `toolUseResult` `{ status: "async_launched", taskType: "local_workflow", taskId, runId, workflowName, summary, transcriptDir, scriptPath }`, and the turn ends (`turn_duration` with `pendingWorkflowCount`). The parser makes a `WorkflowRun` (`parser.workflows`, a `{ kind: "workflow" }` block), ended by its `<task-notification>` (`producer: "session-task"`; `usage` adds `agent_count`, `agents_done`, `agents_error`, `agents_skipped`; `output-file` holds the whole result where `result` is cut with `... (truncated N chars, full result in …)`; `TaskNotification.agents`, `outputFile`, `workflow`). Its agents are not in the transcript: `<session>/subagents/workflows/<runId>/` holds `agent-<agentId>.jsonl` with `.meta.json` (`agentType: "workflow-subagent"`, `description` = label, `workflowPhase`, `model`; no `toolUseId`) and `journal.jsonl` (`launched`, `started` with `agentId`/`label`/`phase`, `result` with the structured result), written as the run goes; `<session>/workflows/<runId>.json` is the run's state (`workflowProgress`: per agent `state`, `tokens`, `toolCalls`, `durationMs`, full `model`), written at its end. `readWorkflow` (`src/transcript/workflows.ts`) fills `run.agents` (AgentRuns keyed `<runId>/<agentId>`, kept across reads, `type` the workflow's name, `phase`, `file`) and `run.phase`; `useTranscript` calls it every `TIMING.workflowPoll` while `workflowDue` (running, or ended since the last read), `loadSession` once. `turnAgents` adds them to the turn's agents (and a workflow notification's), so `a`/`A`, `◆n` and the stats count them; `workflowMarkdown` renders the block in a magenta frame (`BOX_START_MAGENTA`, title `◇ Workflow · …`; with `showAgents`); the full prompt of the notification shows the counts (`agentCounts`) and a JSON result as an indented code block (`notificationResult`, `indentJson`, which also indents cut JSON), and `turnAttachments` offers the output file. Sessions keeps them as `SessionSummary.workflows` (counts from the notification, no folder read: row `◇n`, `Workflows (n)` after Plans, `SESSION_LEGEND`); the export puts the runs' agents into `LoadedSession.agents` and writes a `workflow` block. Agent transcripts: prompt 1 is `[Workflow harness — user request] …` (the relayed request), prompt 2 `[Workflow harness — computed task] …`, each a preamble line and the text indented by two (`harnessPrompt`, `Turn.harness`, `subagentPromptLabel`); the agent ends with a `StructuredOutput` call (shown as `**Result**` and a JSON block at every tool level), a `structured_output` attachment and the tool result "Structured output provided successfully"; they also hold `api-request`, `api-request-blob` and `api-request-shape` lines (not sidechain, ignored). Background commands of workflow agents pass through the main transcript as `queue-operation` lines only (`remove` with `reason: "absorbed_mid_turn"`).
- Pasted images are `image` content blocks in the prompt (also in `queued_command` prompts). A prompt of images only has no text, so it gets `[Image]` / `[3 images]` as its prompt (`imagesLabel`); otherwise it would start no turn.
- Attachments of a prompt (`Turn.attachments`): its `image` blocks, then `attachment` entries that directly follow it: `inlined_image_paths` (the images' copies in `~/.claude/uploads`, in paste order), `file`/`directory` (@-mentions; `path` is the `displayPath`, relative to the session's folder, `full` the absolute `filename`) and `selected_lines_in_ide`/`_diff`. Any `user`, `assistant` or `system` entry ends that window (`takesAttachments`): after `/compact`, Claude Code writes `file` attachments for files it had read, right after the "Compacted" local command output, and those are not the user's. The prompt text keeps Claude Code's placeholders `[Image #n]`, whose numbers count through the session (not per prompt); `pastedNumbers` (`src/attachments.ts`) maps the images to them in order and numbers images without one after them, `markedPrompt` colours them and adds the missing ones (an `imagesLabel` prompt becomes its marks). Tool results with images or PDFs: `toolOutcome` keeps any tool's `image` and `document` blocks as `ToolOutcome.images` (`ResultImage`: `kind: "pdf"`, `name` from `input.file_path` or `toolUseResult.file.filePath`; Read writes `toolUseResult` `{ type: "image", file: { base64 } }` without a path, `{ type: "pdf", file: { filePath, base64 } }`). `turnScreenshots` numbers all of them per turn, images (browser screenshots and the rest together, `[▣ n]`) apart from PDFs (`[▤ n]`, `Screenshot.kind`); `toolMarkdown` appends the marks to a tool's line and, with tools `off`, gives a call with images a line of its own (`filesLine`: `▣ diagram.png [▣ 2]`), also when copying. `AttachmentItem` (`src/attachments.ts`: `pasted`, `file`, `directory`, `image`, `pdf`) is what can be opened; `turnAttachments(turn)` lists a turn's (pasted, @-mentions, tool images and PDFs), `subagentAttachments` a subagent page's (numbered across the page), `attachmentFile` gives the file: the upload or saved copy, else the transcript's block written to `<tmp>/cco-images/` (`promptImageFile`, `resultFile` in `src/images.ts`, by uuid or `tool_use_id`), an @-mention's `full` path if it exists. `o` opens `AttachmentsDialog`; `Preview`'s `onMark` gets a click on any mark (`markAt` in `links.ts`: `[Image #n]`, `[▣ n]`, `[▤ n]`, in the sticky header too) and `itemOfMark` finds the item. The 📎 line (`attachmentSummary`) counts pasted images, @-mentions, selections, tool images, screenshots and PDFs; the list row shows `▣n` (`mediaCount`: images and PDFs, not @-mentions).
- Prompts typed while Claude is working are not stored as `user` entries. When Claude takes them in mid-turn, they appear as `type: "attachment"` with `attachment.type: "queued_command"` and `attachment.prompt`; `queue-operation` lines only record the queueing. They start their own turn with `queued: true`, shown as `↳` in the list.
- A turn is `done` after an assistant line with `message.stop_reason` `end_turn`/`stop_sequence` (a later `tool_use` line resets it), a `system` entry with `subtype: "turn_duration"` or `local_command`, or `<local-command-stdout>` output. `[Request interrupted by user]` and `[Request interrupted by user for tool use]` arrive as `user` text entries and set `interrupted` (`user`/`tool`) on the last turn. The chat shows a `Spinner` for the last turn while it is neither, but only when the viewer follows the running session (`liveSession`; a session viewer, `--session`, only while that session runs in a Claude Code); the demo fixture's answers therefore carry `stop_reason: "end_turn"`.
- The `ExitPlanMode` line is only written once the user decided. For the plan being written, `plan_mode` attachments (`attachment.planFilePath`, not for subagents) start plan mode and `plan_mode_exit` ends it (`TranscriptParser.planMode`); the Plan view shows that file as a `draft` while it is newer than plan mode's start and differs from the plan presented last (`draftPlan` in `PlanView.tsx`).
- A tool call is written to the transcript only once the tool has finished (with its `tool_result` right after), so a running command or an unanswered `AskUserQuestion` is not in the file yet. Each `tool_result` entry carries a structured `toolUseResult` that differs per tool (Bash: `stdout`/`stderr`/`interrupted`; Read: `file.{startLine,numLines,totalLines}`; Edit/Write: `structuredPatch`; Grep/Glob: counts and `filenames`; AskUserQuestion: `answers` question → label or typed text, `annotations`). `toolOutcome` (`src/transcript/tools.ts`) reduces it to what the chat shows when the result arrives, so no file contents are kept; `toolMarkdown` renders a call at the `showTools` level (`off`/`compact`/`full`); with `off` only questions, framed (`questionMarkdown`), with the other levels they are a `⚙ AskUserQuestion` line like other tools. Claude in Chrome calls (`mcp__claude-in-chrome__*`, `src/transcript/chrome.ts`) get one line per action, symbol and verb first, without tab ids (`↗ navigate`, `⊙ click`, `▣ screenshot · 1568×744`); a `browser_batch` lists its `actions` with the matching `[name] result` texts (`ToolOutcome.steps`). Their results are text blocks: the result, `image` blocks, a `Tab Context` (the executed tab's title becomes `ToolOutcome.page`) and sometimes a `<system-reminder>`, which is dropped. `turnMarkdown` writes `*on <title>*` whenever the page changes: before the action, after a `navigate`. The desktop app's Browser pane (`mcp__Claude_Browser__*`, from a cloud session `mcp__remote-devices__Claude_Browser__*`) has the same tools plus `preview_start` (opens the pane, JSON result) and `tabs_select`; its tab ids are words (`seed`, `tab-1`), clicks carry an `action_summary` (shown instead of the ref or point), results end in `(captured at origin …)` (dropped) and each image is followed by `[Image: source: <session>/tool-results/…jpg]`, its saved copy (`ResultImage.path`). `isBrowserTool` covers all three prefixes. With `showTools` `off`, `turnMarkdown` frames each run of browser calls that Claude's text does not interrupt (hidden tools do not) in a cyan box (`BOX_START_CYAN`, title `Claude in Chrome`/`Browser` with counts; `browserItems`: a list item per action, a batch's each, with `ToolOutcome.brief` dimmed below: find matches, a script's value of several lines, console messages), and collapses two page lines in a row. Images of browser results are `ToolOutcome.images` (with the batch `step`); `turnScreenshots` numbers them through the turn (`answerLines` passes them to each run), and every level marks them `[▣ n]` (`shotMark`), on screen followed by a dimmed `(o)` (`shotHint`, `SHOT_HINT`; not when copying or exporting). `Preview`'s `onShot` opens a clicked mark (`shotAt`); `o` always opens the `ImagesDialog` (`src/tui/ImagesDialog.tsx`, modal through `onModal`; also for a single image), which lists the prompt's pasted images, then the screenshots (`turnImages`), starts on the last and stays open after Enter; `screenshotFile` (`src/images.ts`) uses the saved copy or writes the result's base64 block, found by `tool_use_id`, to `<tmp>/cco-images/`. `c` copies without the frames (`browser: false`).
- Turn stats (`Turn.stats`, `src/transcript/turnStats.ts`): created by the turn's first assistant line that is not `<synthetic>`, numbers only, so they survive `SessionReader` dropping the blocks. `message.usage` repeats on every line of a `message.id` and counts once (`trackUsage` replaces the previous line's share); `context` is input plus cache of the last response, `output` the sum. Tool calls are counted at `tool_use` (`addToolCall`, also per name in `toolNames`), files at a successful Edit/MultiEdit/Write/NotebookEdit result (`addFileChange`: Write `type: "create"` is `new` and counts its content's lines, the rest `structuredPatch`; per file in `lines`, summed in `added`/`removed`); deletions are not in the transcript. `durationMs` comes from `turn_duration`, else the time to `end` (the turn's last entry). `turnStatsLines` in `ChatView.tsx` renders them below the prompt, the first line marked with `$` (`statsRows`; also for compactions and continuations), counting up every second while the turn runs; the header is memoized apart from the body so that tick does not re-render the answer. The full prompt (`Enter`) ends with `turnDetailLines`: a `$ Details` heading and rule, then the time span, tokens per model, tools per name, each agent and each file with its lines (paths sorted, counts aligned while they fit), for every turn with stats; rendered apart from `fullPrompt`'s memo for the same tick.
- Plans are `ExitPlanMode` tool calls (`input.plan`). The user's decision is the matching `tool_result` in a later `user` entry: `is_error: false` means approved, `is_error: true` rejected, with optional feedback after "the user said:". `TranscriptParser.plans` collects them; Claude Code also writes plans to `~/.claude/plans/`, but with random names and no project, so the transcript is the source.
