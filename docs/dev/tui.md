# TUI

Ink 7 + React 19, `src/tui/`: the shared list and preview, mouse, keys and the frame buffer.

**TUI** (Ink 7 + React 19, `src/tui/`):
- `App.tsx` reads the transcript once (`useTranscript`) for the chat and plan views and keeps all views mounted (hidden with `display="none"`) so the chat keeps following while the git view is shown. Views use `useInput(..., { isActive })`.

- Mouse (`src/tui/mouse.ts`, setting `mouse`): `App` turns on reporting (DECSET 1002 + 1006, SGR: presses, releases and moves with a button held); Ink hands each report to `useInput` without the ESC (`"[<0;12;5M"`), which no key binding matches. `useMouse()` parses them for the view whose `MouseContext` (set by `App`: shown, no dialog, setting on) is true. `Screen` puts the list and preview into `AreaContext` (their cells on the terminal), so `List` (`onPick`: click selects, wheel moves) and `Preview` (`onWheel`; a click on a URL opens it via `linkAt` in `links.ts`, which joins URLs wrapped over full lines, on release) map positions themselves. `App` takes clicks on the top bar's tabs itself (`tabAt`, from the same `TABS` that `Tabs` draws). `List` ignores `drag`/`release`/`right`. A double click on the selected entry does what `Enter` does in every view (`doubleClicks` in `openKey.ts`, through `List`'s `onClick`; Settings' `activate`); `↓ more ↓` loads with a single click, dialogs take no mouse. A drag in the preview selects its lines (`src/tui/selection.ts`: `Point`s in line and unshifted column, both ends included; started right of `frozen`, the gutter is left out; the sticky header is a `Region` of its own, without its closing rule and, past column 2, without `previewHeader`'s marker and indentation), `highlightColumns` inverts them without their colours, and the release copies `selectedText` and shows a `copied N lines` badge in the bottom row for 1.5 s. The selection holds the text of its first line and counts only while that is unchanged (another entry, a new width); a click or the right button (`right`, anywhere) drops it. Ctrl+C does not quit (`src/tui/ctrlC.ts`): Windows Terminal copies with it only while it has a selection of its own, so a Ctrl+C after a drag reached Ink as `\x03` and closed the pane. `watch.ts` hands Ink a stdin (`withoutCtrlC`) whose `read()` drops it and calls the `onCtrlC` listeners (with `exitOnCtrlC: false` alone, every `useInput` would get it as `c`); `App` then calls the shown preview's copy (`CopySelectionContext`, registered while it has a selection) or shows `Ctrl+C does not quit: q does`.
- Reload (`F5`, `Ctrl+R`; `src/tui/reload.ts`): Ink's `useInput` reports every function key as an empty input with no flag, so `useReloadKey` listens for the raw `ESC[15~` on the stdin context's `internal_eventEmitter` (`useStdin()` returns the whole context at runtime). `App` counts reloads per view and hands each view a `ReloadContext` (`count`, `status`, `done`); nothing is remounted, so selection, scroll positions and open details stay. Data sources depend on `count` (`useOnReload` runs on each reload, not on mount): `useTranscript`/`useSessionPath` take `reloads.chat + reloads.plan` and read the transcript with a new parser, keeping the old turns shown until then (`loaded` tells `App` it is done); `useSubagent`, `usePlanFile`, `useFavorites` read again; Sessions and Monitor scan with a new index (no partial lists during it); Git looks up the repository again and refreshes; Settings calls `reloadSettings()`; `useListFilter` drops its filter. `Screen` shows `reloading…`/`reloaded` ahead of the status. A control-only write (`?25l`) makes the frame buffer redraw in full. Views skip `isReloadKey` where a plain `r` is bound (Settings). F5 is ignored while a dialog or a reload is running.
- List range (`src/tui/loadMore.tsx`, settings `sessionsRange`/`monitorRange`: `today`, `7d`, `30d`, `90d`, `all`): `useListRange` gives `since` (`rangeStart`: local midnight of the first day, today counted) until `↓ more ↓` (`LOAD_MORE`, an entry at the oldest end of the list, a centred badge like `moreBadge`: `centredBadge`) reads the whole history; that stays in the view's state until the viewer restarts, also when the setting changes. The entry stays until that scan has finished (`showsLoadMore`, `complete` from the data hook), showing its progress; then the selection goes to the newest entry read (Sessions: `loadedAfter`; Monitor keeps the index). `SessionIndex.scan` and `ResponseIndex.scan` take `since` and skip transcripts last written before it (`writtenSince`); Sessions then keeps the sessions whose `lastActive` (last write) is since then (plus the active and running ones), Monitor the responses (`measuredSince`, so the usual values only come from the range). `useListFilter`'s `keep` keeps the entry through a filter and out of the counts; `List`'s `onClick` (a click, not the wheel) loads.
- List order: Chat, Plan, Sessions (and trash) and Monitor keep their data in its natural order (oldest first; Monitor days and the trash newest first). Sessions is always shown `reversed` (newest first) and Monitor never; for Chat and Plan the `*Order` settings only mirror the display: `List` with `reversed` renders bottom-up and maps `onPick` back, `orderedNav` swaps ↑/↓ and first/last for `handleNavigation`, and `useListFilter`'s `nextMark` takes Shift+↑/↓ in screen order. Follow logic, positions and marks stay on the natural index.
- List filter (`Ctrl+F`, `src/filter.ts`, `useListFilter` / `FilterDialog` in `src/tui/`): a display layer like `reversed`. Each view gives `useListFilter` its items, texts per item (`FilterText`: `list`, what the row shows, and `details`, what the preview adds; the `filterIn` setting, switched with `^L`/`^D` in the dialog via `toggleFilterIn`, picks; each a `haystack`: fields joined by newlines, so `*`/`?`/`_` stay within one) and its natural `selected`/`select`; it returns `shown` (natural indexes, passed to `List`, which maps `selected`/`onPick`/`itemKey` before reversing), `nav` (already `orderedNav`), `last` (newest shown: Chat and Plan follow it), `nextMark(dir)` (Shift+↑/↓: the next marked entry shown, down or up the screen, from the view's `marked`), `pinned`/`unmarking` (below), `none`, `count`, `banner` (passed to `List` as `filter`: its top row shows the filter, the entries and the mouse area start one row lower), `footer` (`^F filter` only while none is on) and the `dialog`. An effect moves a hidden selection to the nearest shown one before it. While the dialog is open the view's own `useInput` is off and `App` ignores its keys (`onTyping` → `typing`, not `modal`, so the wheel still reaches the list). Texts are only built while a filter is on. The Sessions trash has none (`enabled: false`); the filter state lives in the views, so it survives view switches but not a restart.
- Pinned group (setting `pinnedFavorites`, formerly `pinnedGroup`, which `readSettings` takes over; default off; `src/pinned.ts`): every list but the trash shows its marked entries once more at the top. Sessions also pins the active and running sessions while `pinnedSessions` is on (default; independent of `pinnedFavorites`), through `useListFilter`'s `pin`. Also a display layer, computed in `useListFilter` from the view's `marked` and `pin`: `screenOrder` (the shown entries top to bottom, bottom-up when `reversed`), `pinnedRows` puts copies of the marked ones above all of them (`{ order, count, row }`, undefined when none shown is marked) and `List` takes it as `pinned`, which replaces `shown` and `reversed`. An entry can have two rows, so the views still select by natural index, and `useListFilter` keeps which copy is selected (`groupCopy`: the entry whose pinned copy it is; any other `select`, such as following or a restored position, lands in the list below). `row` is the selected row; `PinnedList` hands `ListRows` the rows as items, keys the copies apart (`★` before `itemKey`) and lets `choose` hear the row a click or the wheel picks. It puts `── ★ Pinned ──` above the group and, above the list, its first separator (groups taken in natural order) or a plain line (`ruleText` of `""`); `listRows` takes the separator labels per item (`heads`, several allowed) and `tops` for the `▲` row. A marked entry shows its `★` in both rows. With the group, `nav` steps through the rows (`stepRow`; Home/End the ends), `nextMark` only through the pinned ones (`nextPinnedRow`: from the list below only up, to the last), and a view calls `unmarking(index)` before unmarking an entry: a selected pinned copy hands the selection to the next pinned row (`afterUnpin`: below, else above; the only one stays with its entry, in the list), one in the list keeps it, and one that stays pinned (`pin`) changes nothing. A selected copy whose entry leaves the group otherwise (a session that ended) hands the selection on the same way (`afterLeaving`, an effect comparing the group with the one rendered before). Which row is selected survives restarts: views pass `copySelected` to `usePositions`' `select` (undefined keeps what is stored for the same entry) and `restoreCopy` (the stored entry, when `pinned`) to `useListFilter`, which waits until the view has selected that entry and then selects its copy, or leaves it in the list when it is no longer pinned; any step, click or mark jump of the user's ends the wait.
- Date separators (`src/tui/days.ts`, setting `dateSeparators`, read in `List` and `SessionsView`; off, Sessions and trash rows show `MM-DD HH:MM` again): `List` with `time` puts a `── Mon 28 Sep 2026 ──` row above each day's items (`listRows`), in display order, so also above the group when `reversed`. `entryGroups` (natural order) gives an item without a time the day before it and returns none when all items are from today (checked at render, no midnight timer). With `period="year"` (Monitor's days) the groups are years (`"2026"`: `periodLabel` tells them apart by length), none while all are from this year; the rows then leave the year out of their date. The rows are not items: `selected`, `onPick` and marks stay item indexes, `listWindow` runs over the rows, a click on a separator picks `before`, and the `▲` row names the day of the first item shown. Sessions and trash rows therefore show only `HH:MM`. With `group` instead (Settings), the separators name each item's group (`ruleText`), always, whatever `dateSeparators` says; a filter shows only the groups with a match. `linesByDay` does the same for pre-rendered lines (the session preview, only for sessions over several days).
- List width (settings `chatListWidth` … `settingsListWidth`, `LIST_WIDTH_SETTINGS`; `hidden`/`narrow`/`normal`/`wide`/`wider`/`full`, `LIST_WIDTH_VALUES`): `LIST_WIDTHS` in `layout.tsx` gives each `ColumnWidth` a share of the pane with min/max columns, `listColumns` keeps the preview 20 columns but never goes below `normal` (the former fixed width). The ends (`ListFold`, `isListFold`) give one side the pane: `layoutOf` sets `Layout.fold`, and `Screen` hides the list box and the preview's border (`hidden`: the preview gets `columns - 1`) or the preview box (`full`); the side out of sight stays mounted with the normal width, its `AreaContext` far below the screen so the mouse misses it. `App` takes `useLayouts()` and hands each view `layoutOf(mode, drilled)`, the dialogs the normal one. `<`/`>` in `App`'s `useInput` step the shown view's width over all six (`stepFold`, `stepListWidth`, stopping at the ends), `|` (`toggleFold`, `src/tui/listFold.ts`) goes from a width to the end not reached last (`FoldState.last`, kept in memory) and from an end back to the width shown before it (`before`, which `App` notes from the settings each render; unknown after a restart, then `narrow`/`wider`); every change is stored. A detail opened while `full` (`setDetail`, all views but Sessions, whose detail is the trash; Monitor reports its table through `onTableOpen`, and `Esc` closes it) sets `drilled` (not stored): the layout is `hidden` until the view reports it closed, so `Esc` goes back to the full list; `|`, `<` and `>` leave it as from `hidden`, keeping the detail open. Each change shows `width: …` in the preview's bottom row (in the list's at `full`) for `COPIED_MS` through `ScreenNoticeContext`: `Screen` draws it below the side cut by a row (`withNotice`), so it also shows over a plain message (no plans, no session), where no `Preview` is; neither the help line nor the info dialog lists the keys (the info dialog fills 24 rows already), the setting's details name them.
- `layout.tsx` holds the shared pieces: the `Screen` frame, the `List` (its selected row spans the list's width: a filler of spaces in the same style follows the entry, since Ink drops trailing spaces; its window is kept between renders and scrolls only once the selection reaches the upper or lower third, `scrollMargin`, and only as far as needed, also for jumps: `nextWindow` in `ListRows`, which keeps the selected entry on its screen row when entries come or go around it and an entry picked with a click under the pointer; a new list, one that fits again, or a change of the `centre` prop, which Chat, Plan, Monitor and Sessions change when they restored the stored selection and Sessions for the trash, centres it), `useScroll`, `handleNavigation`, `previewHeader`, `Marquee`/`EntryText` (the selected list entry scrolls, at most `MARQUEE_MAX_SCROLL` = 250 columns, then starts over; `lead` colours its first columns, e.g. a slash command's name from `commandName` in the chat, also while it scrolls: `leadParts`) and `wrapPath`. All views share the same navigation (`handleNavigation`, `markKeys`): `↑↓` switch item (also in detail views: full prompt, whole file, plan changes, Monitor table; on a subagent's page they switch turns and close it, `a`/`A` step through the agents), `PgUp/PgDn` scroll the preview by page and `Ctrl+↑↓` by line, `Home`/`End` first/last item, `Ctrl+Home/End` top/bottom of the preview, `Space` marks, `Shift+↑↓` jumps between marks (swallowed where there are none), `Ctrl+←→` scrolls sideways. Plain `←→` switch views like `Shift+Tab`/`Tab` (`App`'s `useInput`, hidden views skipped, wrapping around; not with Ctrl, Shift or Alt, and not while a dialog takes the keys, e.g. the filter's cursor); `b` does nothing. Only `q` quits: `Esc` closes what is open (detail, trash, dialog) and otherwise does nothing, so a key meant for Claude Code does not close the pane.
- The top bar status shows counts and positions only. Whether an option is on (follow, tools, wrap, all projects, …) is shown by the help line, which highlights `FooterItem`s with `on`; do not repeat it in the status. `Screen` adds the version at the right end, but only if tabs and status leave room for it (measured with `measureElement` after each render), so it never cuts the status. Right of it, a cco run from a checkout shows ` DEV ` (`DEV_LABEL`, white on `#d02020`, brighter than the red session bar) whatever fits: `App` and `RcViewerApp` provide `DevContext` (the click handler) when `devInstall.get()` says so, and `test/setup.ts` turns that off, since the tests run from the checkout. A click on it opens `DevSwitchDialog` (see `docs/dev/features.md`, updates).
- Terminal title (`src/tui/title.ts`): `App` sets it with OSC 0 to the session title, else the project folder. The title comes from `TranscriptParser.title`: the last `custom-title` entry (`/rename`) over the last `ai-title` one (Claude Code's generated title); Claude Code repeats both entries throughout the transcript. Like Claude Code's (`claude.exe`: `["◐","◑"]` every 960 ms while busy, else `✳`), the title starts with a status mark (`titleWithStatus`): ◐/◑ while the last turn is neither done nor interrupted, ✳ otherwise; a session viewer's (`--session`, `--remote`) has the mark only while its session runs. `FrameBuffer` passes a write of only OSC sequences through without redrawing the next frame in full (`OSC_ONLY`), since the mark changes every second. The session colour (`/color`) is an `agent-color` entry (`agentColor`: red, orange, yellow, green, cyan, blue, purple or pink), also repeated; `TranscriptParser.color` keeps the last one, and `App` hands it through `SessionColorContext` to `Screen`, whose top bar takes a dark shade of it (`SESSION_BARS`, darker while unfocused; `barBackground`). Unknown names count as none, which keeps the blue focus bar.
- `Preview.tsx` renders a sticky `header` (prompt or file path, capped by `fitHeader`) above the scrolled lines. Like the list, it turns the first/last row into a centred blue badge `↑ N more lines (ctrl+Home)` / `↓ … (ctrl+End)` when lines are hidden (`previewWindow`, `moreBadge`; the Chat's former "Jump to bottom" footer is this badge now). A click on a badge calls `onJump` (the Chat: `jumpToTop`/`jumpToBottom`, which also resumes following), else scrolls through `onWheel`; the row covers the line at `scroll`, so jumps to a line (hunks) scroll to one line before it. A scroll bar (`scrollThumb`, dim `│` track, the thumb a space on a gray background: `┃` and `█` leave gaps between rows in many fonts) takes the column right of the preview, which `useLayout` leaves free; the thumb touches the track's ends only at the very top or end, and a click on it jumps (`scrollAtRow`, through `onWheel`). `Scroll.position` (`scrollPosition`) is `top`, `end`, `121–160/300` or `all`. `spinner={{ line, active }}` replaces the first character of one line with a `Spinner` while it is visible ("Claude is working…"), so the pre-rendered lines stay memoized.
- All content is pre-rendered into ANSI strings that are already wrapped to the preview width, then sliced by scroll offset. Ink does no wrapping of its own here (`wrap="truncate"`).
- Double buffering (`src/tui/frameBuffer.ts`): Ink redraws every frame in full, and on Windows it clears the whole screen first whenever the output fills the terminal (`isWindowsConsole` in `ink.js`), which `Screen` always does; under load the terminal shows the empty screen in between. `cli.ts` hands Ink `frameBufferedStdout(process.stdout)`, a `Proxy` whose `write` goes through `FrameBuffer`: it strips Ink's frame prefix (`clearTerminal` or `eraseLines`), diffs the lines against the screen last written and writes only changed ones with absolute cursor positions (`ESC[K` only after lines narrower than the terminal, pending wrap), as one write in synchronized output (Ink's own separate `?2026h/l` writes are dropped). Control-only writes (alternate screen, cursor, focus/mouse reporting; not the window title, see above) pass through and, like `resize`, make the next frame a full redraw, which clears the screen and the scrollback (`2J` `3J`: Windows Terminal moves what `2J` erases into its scrollback, and the mouse wheel then scrolls the whole pane to old frames). Without a known prefix, a write counts as a frame only if it does not start with a cursor or erase sequence (the first frame starts with text or a colour); anything else passes through. An Ink update that changes the prefixes must be checked against `test/frameBuffer.test.ts`. `CCO_FRAME_BUFFER=0` turns it off.
