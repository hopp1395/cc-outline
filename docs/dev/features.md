# Monitor, updates, doctor, prompt editor, / commands, progress, clipboard, focus

**Monitor** (`src/monitor/`, `MonitorView.tsx`): `ResponseReader` reads every transcript (and `<session>/subagents/*.jsonl`, `subagents/workflows/<runId>/agent-*.jsonl`) incrementally and keeps one small `Response` per API response: `start` = the timestamp of the `user` entry before it (prompt or tool result; main and sidechain tracked apart), `first`/`end` = its first and last line with that `message.id`, `model`, `output_tokens`. `<synthetic>` messages are skipped; `isApiErrorMessage` entries are the only errors transcripts have. Speed = tokens / (end − start), wait = first − start; responses under 0.5 s, over 10 min or under 50 tokens are counted but not timed. `dayBuckets`/`typicalBuckets` take medians per stretch (local time), `barChart` draws them in eighths. The overall index (`scoreOf`, `dayScore`) is the geometric mean of speed / usual and usual / wait × 100; the day's is weighted by each stretch's `measured` responses. `Enter` swaps the chart for `responseTable` (one row per response, index against its stretch's usual values), which keeps its scroll position under `<day>#table`. `IncrementalFile` (`src/transcript/incremental.ts`) is the byte-offset line reader shared with `SessionReader`.

Updates (`src/update.ts`, `src/tui/useUpdate.ts`): `App` runs `useUpdate` once, which reads `~/.claude/cco/releases.json` at once and, unless the `updateMode` setting (label *update*: `on`/`off`/`auto`; default `auto`; of the former boolean `updateCheck` only `false` is kept, as `off`) is `off` at the start, asks npm (`registry.npmjs.org/cc-outline/latest`, the version `npm install -g` gets) and GitHub (`/repos/hopp1395/cc-outline/releases`, the notes `/cco-release` writes) once, with global `fetch`; a source that fails keeps its cached part (`mergeReleases`, `stale`). F5 in Settings asks again. With `auto`, `offer` turns true once that start check finds an `update`; `App` then shows Settings on the `update` entry with `select.ask`, and `SettingsView` opens the update confirmation right away (once per viewer start). `UpdateContext` hands the result to `Screen` (the version label becomes ` v0.7.0 → 0.8.0 `, else ` ↑ 0.8.0 `; unlike the version it always shows, the status is cut; a click calls `open`) and `SettingsView` (a Releases group after Reset, the last one: `update`, `release:<tag>` entries, or a `releases` note; the view keeps its selection by key, since the releases arrive later). `updateState`: `update` for an npm install (`installKind`: the package folder is `node_modules/cc-outline`; a checkout run through `npm link`, whose path Node resolves to the checkout, or an npx cache is `dev` and only told), `restart` when the `package.json` on disk is newer than the running `VERSION` (another viewer updated). `runUpdate` runs `UPDATE_STEPS` (npm, marketplace, plugin) one by one with `shell: true` (npm and claude can be `.cmd` shims, which Node 22 starts only through a shell) and `independentEnv`, stops at the first failure and leaves the rest `pending` (`remainingCommands`, `c` copies them); while it runs, the view is modal and the progress dialog (see below; from the confirmation on: `Updating – <step> (n/3)…`, no cancel; after a failure the end of its output, `c`, Esc) shows it, since npm prints nothing for a long time and the preview alone looked as if nothing happened. Once all succeeded, the dialog says `Restarting…` for `TIMING.restartDelay` (1 s; if it cannot reopen, `reopenFailed`, it says to do so by hand); then `moveViewer(…, updatedTo)` starts the new CLI (`cco open --after-pid --updated-to`), which reopens in the same place and view; `--updated-to` reaches `App` and the top bar says once that Claude Code needs a restart for the plugin. What's new: `takeSeenVersion` keeps the newest version a viewer ran in `~/.claude/cco/version.json`; a viewer of a newer npm install gets the one before and `useUpdate` returns `whatsNew` (`releasesBetween` it and `VERSION`, from the cache the old viewer's check filled), which `App` shows in `WhatsNewDialog` (modal, part of `blocked`) until `closeWhatsNew`. The old viewer's code starts the update, so no new flag can carry the old version; without a seen version but with `updatedTo` (updated from a version before this), the notes start after the release before `VERSION`. `--select <entry>` (`/cco:releases`: `releases`) goes to a new viewer as an option and to a running one in the control file (`ControlRequest.select`). `cco open --action` does the same for `ControlRequest.action` (`VIEWER_ACTIONS`): `restart` (`/cco:restart`, no `--view`: a running viewer keeps its view and reopens through `restartViewer`; without one, a new viewer opens in the session's last view) and `update` (`/cco:update`: Settings on `update`, `recheck()` whatever `updateMode` says, then the confirmation if it found an update; a new viewer gets `--action update`). `useViewerControl` keeps its first callback, so `App` passes the current `onRequest` through a ref. Tests stay offline: `test/setup.ts` (vitest `setupFiles`) stubs `fetch`.

Doctor (`src/doctor.ts`, `cco doctor [--fix]`, `/cco:doctor`, Settings' Reset entry `reset:doctor`): `diagnose` runs the checks per `DOCTOR_GROUPS` (Installation, State files, Settings, Environment, Hooks) and returns `Finding`s (`ok`/`warn`/`error`, text, hint, paths, `Repair`); a check that throws becomes an error finding. Findings that share a repair name the same `Repair.id` (every key of `settings.json`), and `repairsOf` keeps each once. A repair either `apply`s file changes in-process or runs `commands` (the plugin update, only for an npm install) through `runCommand` of `update.ts`; `runRepairs` runs every step, also after one failed, unlike `runUpdate`. The plugin is read from Claude Code's `plugins/installed_plugins.json` and `enabledPlugins` in its `settings.json`, which cco never writes. State files: names are matched by pattern (`<slug>.claude|viewer|control-<pid>.json`, legacy `.viewer.json`/`.control.json`, `<slug>.json` minus the global files, `<file>.<pid>.tmp`, `debug-<pid>.log`); files that are no JSON object are renamed to `.corrupt` and count as leftovers after 7 days. The hooks are checked only while a Claude Code runs in the project (`runningSessions`): the newest `updated` of its `claude-<pid>.json` and `<slug>.json` must not be older than the last prompt in its transcript (`lastPromptTime`, from the last 512 KB; tool results, meta, shell and local commands skipped). `cco doctor` exits 1 if an error is left; `cli.ts` imports `doctor.js` dynamically so the hook stays fast. `/cco:doctor` runs it without `--fix` and lets Claude summarize. In Settings nothing is checked until `Enter` (or a double click, both `activate`) and a confirmation; it then checks group by group (`diagnoseGroup`), each after a pause of `TIMING.checkStep` (300 ms) while the progress dialog shows `Checking – <group> (n/5)…` (`checkProgress`, also on F5 and after a repair; a failed repair's dialog stays in front; `DoctorChecking`; a newer check stops an older one through `checkRun`). The report is kept in state (`DoctorCheck`, with its time) while the viewer runs. With repairs on offer, `Enter` asks to repair instead, and the run is modal like the update, with the same progress dialog (`DoctorRun`, `repairProgress`; it closes by itself when all repairs worked; after a failure `c` copies the commands of the failed repairs, `failedRepairCommands`); afterwards, and on F5 once checked, it checks again.

Prompt editor (`src/tui/PromptEditor.tsx`, `src/promptDraft.ts`, `src/clipboardImage.ts`, `src/promptEdit.ts`, `src/editor.ts`): `e` in the viewer (not a remote viewer, which has its composer) opens it over the whole pane (`App`: `editor`, part of `blocked`; an absolute `Box` around it), only where the prompt and the focus can go to its Claude Code (`editable`: `types` and `canFocusViewer`; else a notice, and the info dialog leaves `e` out). Enter is a new line; Ctrl+Enter (a `
` in Windows Terminal, like Ctrl+J; `isCtrlEnter` also takes CSI u and modifyOtherKeys), Ctrl+S and the button `HAND_OVER` (clickable: its cell from `layout`) hand over. Alt+V, or a paste without text (Windows Terminal pastes Ctrl+V itself and brings nothing for an image), runs `readClipboardImages`: on Windows `CLIPBOARD_IMAGE_SCRIPT` (PowerShell `-STA`, System.Windows.Forms: FileDrop as `file	<path>` lines, copied by node if an image extension; else the `PNG` stream; else `GetImage()` as PNG into `CCO_IMAGE_FILE`), macOS osascript, Linux wl-paste/xclip; into `promptImageDir()` (`~/.claude/cco/images`). Images are `[Image #n]` placeholders (`placeholder`, numbers never reused: `nextImageNumber`); `promptText` turns them into the paths in quotes (a typed path is not attached by Claude Code, Claude reads it with Read), `fromPromptText` back. The draft (`PromptDraft`, `~/.claude/cco/drafts/<session id>.json`, `project-<slug>` without one) is saved 300 ms after a change, on Esc and before handing over; the caller clears it once the hand-over worked. `cleanupPromptFiles` (SessionStart hook) deletes both after 30 days. Hand-over from `e`: `typePromptInClaude` (tmux `send-keys -l`; Windows `CONSOLE_INPUT_SCRIPT` with `promptLineSteps`, line breaks as Ctrl+J key events, no Ctrl+L, no Enter; its PowerShell starts 100 ms after the editor opened, since spawning it blocked the first frame for ~200 ms), else the text is copied and the draft kept; either way `focusClaude` then moves the focus to Claude Code's pane (tmux: `select-window` and `select-pane`, also from a window of its own). Ctrl+G: Claude Code runs `$VISUAL "<file>"` through the shell (Windows fallback `start /wait notepad`, the resolved editor is cached until it restarts) and applies `env` of its `settings.json` to its process; *Ctrl+G: cco's prompt editor* (Settings Reset entry `editor`, `setUpEditor`/`removeEditor`, backup `settings.json.cco-backup`, the VISUAL before in `~/.claude/cco/editor.json`) sets it to `editorCommand()` (`"<node>" "<cli.js>" edit`); the doctor's Environment group reports it (`stale` with a repair). `cco edit <file>` (`runEdit`): `findClaudePid` (CLAUDE_PID, else the only running session in the cwd, else the nearest ancestor among `runningSessions`, parents from one `Get-CimInstance` or `ps`), then `editInViewer`: `ControlRequest.edit` (`requestEdit`) to that process's viewer, which answers in `<file>.cco.json` (`open`, `declined`, `done`, `cancelled`; `TIMING.editAnswer` to answer). The viewer takes it only with a Claude Code, not `fixed`, no dialog of a view open and `canFocusViewer` (tmux `TMUX_PANE`, Windows Terminal docked right/left): it reads the file as `initialText` (it wins over the draft's text), moves the focus there (`focusViewerPane`) and back after (`focusClaude`), writes the text into the file. If `cco edit` dies meanwhile (polled), the editor hands over by typing. Otherwise `cco edit` runs the editor itself in Claude Code's pane (`runPromptEditor`, loaded with `importProduction`).

`/` commands (`src/slashCommands.ts`, `src/tui/CommandPicker.tsx`): `SessionComposer` and `PromptEditor` take a `commands` `CommandSource` (`LocalCommandSource`: transcript, cwd, config folder; or `{ remoteId }` where the prompt goes to claude.ai: `App`'s and `RcViewerView`'s `remoteId`, a `twins` session's too; the composer leaves it out while its line is blocked) and `useCommandPicker` opens `CommandList` while `commandQuery` finds a command name being typed (the prompt starts with `/`, the cursor before any space). `sessionCommands` reads them when the list opens (and again once the transcript's mtime changed): the transcript's last `skill_listing` attachment with `isInitial` plus the ones after it (`isInitial: false`, one skill each; `readSkillListing` reads a megabyte at a time from the end; `names` and `content` lines `- name: description`), then `folderSkills` (the config folder's and `<cwd>/.claude`'s `skills/<name>/SKILL.md` and `commands/**.md`, `a/b.md` as `a:b`; the plugins installed for the user or the project and on in `enabledPlugins` of the user's, project's or local settings, `<plugin>:` before each), which adds what the listing leaves out (skills with `disable-model-invocation`, everything before the first listing), then `BUILTIN_COMMANDS`, each name once. `src/builtinCommands.ts` is generated by `npm run commands:builtin` (`scripts/builtin-commands.mjs`: a headless `claude -p --input-format stream-json` answers a `control_request` `initialize` with `commands` `{ name, description, argumentHint, aliases?, builtin? }`, keeping `builtin`, over `TERMINAL_COMMANDS`, a list kept by hand of the commands only an interactive one has, `/resume`, `/exit`, …; recordings given as arguments add theirs) and refreshed by `/cco-release`. A remote session's (`remoteCommands`, `src/remote/commands.ts`, asked again after 5 minutes; a failure is not kept): the Claude app sends `initialize` when it opens a session; a Remote Control session (2.1.310, `test/fixtures/remote-initialize.jsonl`) answers with a `control_response` whose `commands` are empty, then writes a whole `system` `init` event (`slash_commands` names only, `skills`, `terminal_slash_commands`: the ones a phone hides, `exit`, `doctor`, `statusline`, …; 2.1.300 wrote `init` with its session id only). `initCommands` takes the newest such `init` among the events (`slash_commands` without `terminal_slash_commands`, Claude Code's own described from `BUILTIN_COMMANDS`, skills without a description); without one, `sendInitialize` asks and the events are read each second for up to 6 s. `matchCommands`: names (and aliases, a plugin's also by the part after `:`) starting with the text first, then containing it, each alphabetical. Keys: `↑↓` choose, `Tab` takes (`takeCommand`: `/name ` replaces the name typed), `Enter` takes and sends in the composer, only takes in the editor, `Esc` closes until the name changes; a click takes, the wheel moves (the composer needs `MouseContext`, which `App` gives it).

Progress dialog (`src/tui/ProgressDialog.tsx`): every run the user starts shows in the one `ProgressDialog` of `App`: the update, the doctor's check and repair, export and import, the wait for a started Claude Code to attach to (`pairingProgress`) and the restart (Reset entry, `r` in every view but Settings, which asks through `restartAsked` with `confirmQuit`, and `/cco:restart`: `restartViewer` shows `Restarting…` for `TIMING.restartDelay`, then `moveViewer`; if that cannot reopen, `✗` with `REOPEN_BY_HAND`, as after an update). `useProgressHost` holds it (owners set their `Progress`, the one set last shows; its `open` is part of `blocked`, so the views, F5 and the mouse rest) and `ProgressHostProvider` hands it down; views call `useProgress(progress | undefined)`, which sets it when what it shows changes (callbacks count by presence, the dialog calls the latest ones), and `useProgressOpen()` in their `isActive`. Tests that render a view alone wrap it in `ProgressProvider`. A `Progress` is data, not text: the `title` names the run and never changes; `text` is the verb while it runs (`progressText` writes `Verb – step (n/m)…` with `step`, `currentStep` of a run's steps) and the outcome once it has ended; `detail` a dim line below (session, file, `12 of 30 s`); `lines` the result or failure. The mark (spinner, `✓`, `✗`) and the frame's colour (cyan, green, red) tell the state. Only the pairing takes `onCancel` (Esc cancels, footer `Esc cancel`); the others say they cannot be cancelled. A run whose result shows elsewhere (doctor, repair) closes by itself, one whose result is only in the dialog (export, import) stays with `✓` until Esc (`onClose`), a failure always does; `c` copies commands where some are left (update, repair). Background progress (Sessions' and Monitor's `reading n/m`, `reloading…`, `LoadMoreRow`) stays in the top bar.

Clipboard (`src/clipboard.ts`, `useClipboard`; `c` in Chat, Plan and Sessions): no clipboardy (it pulled in execa, cross-spawn, PowerShell calls and a bundled .exe). `clipboardMethod` picks `tmux` (`tmux load-buffer -w -`, which also sets the outer terminal's clipboard; tmux ignores OSC 52 from programs unless `set-clipboard on`), `osc52` in terminals known to support it (Windows Terminal, iTerm2, WezTerm, kitty, ghostty, alacritty, foot), else `native` (pbcopy, wl-copy/xclip/xsel, `clip` with UTF-16 and BOM). If no program works, it writes OSC 52 anyway. The sequence goes through Ink's stdout; `FrameBuffer` passes a write of only OSC sequences through.

Focus indication (`src/tui/focus.ts`): the viewer enables terminal focus reporting (DECSET 1004). Ink passes the reports to `useInput` as `"[I"` and `"[O"`, with the ESC stripped and no key flags set, so no view binding reacts to them. `FocusContext` feeds `Screen` (top bar, footer) and `List` (selection style). A pane opened with `keepFocus` starts with `--unfocused`, because the terminal sends no initial report. Windows Terminal 1.12 sends no reports at all, so `focusFromInput` also counts any key or click as focus in, and `App` passes the time of the last prompt typed after the viewer started (`typedInClaude`) as focus out.
