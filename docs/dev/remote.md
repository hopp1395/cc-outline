# Remote sessions, session viewers and the Remote Control Viewer

- Remote sessions (experimental, `src/remote/`, setting `remoteApi`, off by default; `sessionsRemote` `show`/`hide` is the fourth part of the filter, `SessionFilter.remote`, its group in `SessionFilterDialog` only with `remoteApi`): Remote Control sessions from claude.ai, through the undocumented `GET /v1/code/sessions` and `…/{id}/events` (reverse-engineered, see claude-rc-api; nothing official, so `api.ts` checks every shape and a surprise is a `RemoteError` `format`; only GET, `remote.fetch` is what tests swap). `readLogin` (`credentials.ts`) reads the access token from `<config folder>/.credentials.json` on every request, never writes or renews it (Claude Code rotates the refresh token), and wants the scope `user:sessions:claude_code` and `Account.organizationId` (`oauthAccount.organizationUuid`, header `x-organization-uuid`); `RemoteError.kind` says what is missing (`no-login`, `expired`, `no-scope`, `no-org`) or what claude.ai answered; the top bar shows it, the last list stays. A company proxy needs the system CAs: `trustSystemCertificates` calls `tls.setDefaultCACertificates` where Node has it (not verified on Node 22; a TLS error says to start with `NODE_OPTIONS=--use-system-ca`). `useRemoteSessions` lists every 3 s while Sessions is shown (`RemoteSessions.list`: `remoteSummary`, no events: title, times, `SessionSummary.remote` with worker/connection status, `userMessages`, `refs`), `useRemoteDetail` reads the events of the selected one (`listEvents`: newest `EVENT_LIMIT` by `sort_order=desc`, no cursor known, so older ones are flagged `truncated`) through `toTranscript` (SDK messages as transcript lines: `uuid` `remote-<sequence_num>` if none, `result` as `turn_duration`, `init`/`stream_event`/`control_request` and the rest counted in `RemoteInfo.unknown`, shown in the header) into the `SessionReader` through `push`; `path` is the stand-in `claude.ai/<id>.jsonl`, which makes `projectName` `claude.ai`. `listSessions` asks for `?limit=100` (without it claude.ai sends 20, and `status=active` is ignored), and `RemoteSessions.list` keeps what the Claude app lists, the sessions whose `status` is not `archived` (a Remote Control session ends archived when its Claude Code exits). A remote session of the list is dropped when one of this machine's sessions read is the same and that session shows `⇄`: Claude Code writes `{ type: "bridge-session", sessionId, bridgeSessionId: "cse_…", lastSequenceNum, ownerAccountUuid, ownerOrganizationUuid }` into the transcript when Remote Control connects it, which `SessionReader` keeps as `SessionSummary.bridgeIds` (merged along a chain); failing that, a UUID in the remote session's JSON (`RemoteInfo.refs`); `passesFilter` lets remote ones through unless `hide`, whatever folder or account; `resumeCommand` is the address `https://claude.ai/code/<id>`, `Enter` offers only copying it, `d`, rename, export and the account options do not apply. A recording from the Claude app (`test/fixtures/remote-capture.jsonl`, `test/remote-viewer.test.tsx`) settled the formats: each event is `{ sequence_num (string), event_id, event_type, source: "worker" | "client", created_at, payload }` (`RemoteEvent.source`); a prompt from the phone is a `client` event `{ type: "user", uuid, client_platform: "ios", message: { role, content: "text" } }`; a question is a `worker` `control_request` `{ request_id, request: { subtype: "can_use_tool", tool_name: "AskUserQuestion", display_name, input, tool_use_id, requires_user_interaction } }`, answered by a `client` `control_response` `{ response: { subtype: "success", request_id, response: { behavior: "allow", toolUseID, tool_name, updatedInput: { questions, answers } } } }`; the app interrupts with a `client` `control_request` `{ request_id, request: { subtype: "interrupt" } }` and sends `initialize` when it opens the session. While a question waits, the list entry has `worker_status: "requires_action"` and `external_metadata.pending_action` (`tool_name`, `input`, `suppressed_request_id`). `pendingRequests` (`pending.ts`) gives the worker's `can_use_tool` requests with no `control_response` or `control_cancel_request` for their id. Remote viewer (stage 2a): a session viewer (see *Session viewers*) of a `◈` session, `cco watch --remote <id>`; `watch.ts` calls `setSessionViewer(true)` (the chat and its own settings, `SESSION_VIEWS`: `isViewShown` says no to the rest). `App` with `remoteId` takes `useRemoteTranscript` (newest events, then each `TIMING.remotePoll` the newer ones by `sequence_num`, the list every third poll for title and status; it publishes only on a change) instead of `useTranscript`, `path` is `remotePath(id)`, and like `--session` it is `fixed` (no `p`, `r`, restart, view per session); a read error shows as the screen notice. Remote control (stage 2b, setting `remoteControl`, off by default, needs `remoteApi`): `sendPrompt`/`sendInterrupt` (`api.ts`) POST `{ events: [{ payload }] }` to `…/{id}/events` with the same headers (`anthropic-client-platform: web_claude_ai`: another platform makes the worker treat the prompt as a peer's message); a prompt is `{ type: "user", uuid, message: { role: "user", content } }`, an interrupt `{ type: "control_request", request_id, request: { subtype: "interrupt" } }`, as the app writes them. `remoteOptions(workerStatus)` (`useRemoteControl.tsx`) orders the actions (`requires_action`: *Answer it*, disabled until stage 3, then interrupt and prompt; `running`: interrupt, prompt; else prompt); `useRemoteControl` runs them, a prompt through `PromptDialog` (several lines: `Ctrl+J` arrives as `\n` without the return flag, `promptRows` cuts by line break and width, drafts kept per session id in memory while the viewer runs), and reports in `notify`. Sessions puts them first in a `◈` session's Enter dialog. A remote viewer's `SessionComposer` (see *Session viewers*) sends while `remoteControl` is on, read live (`App`: its `PromptChannel` `blocked` without it; `composer`; `composing`, which starts false: the chat has the keys until `Tab` or `i`; the chat gets `shorter(layout, composerRows)`, the rows the composer reports through `onHeight` from `measureElement`), Claude Code's prompt line: while it has the keys, `App` ignores them (`typingInComposer`) and `ChatView` takes only PgUp/PgDn (`scrollOnly`; the wheel goes through the mouse as before). It grows to six rows (`TextRows`, `promptRows`), `Ctrl+J` new line, `Enter` sends (`sendPrompt`, cleared once sent), `Esc` interrupts while Claude works (`working` or `workerStatus` `running`), else hands the keys to the chat; `Tab` or `i` in the chat take them back (`App` only while the chat is shown; in Settings `Tab` switches the view, and `typingInComposer` holds only in the chat). A pending request (`remote.pending[0]`, else the list's) takes its place: a permission panel (`permissionResponse`, `toolInputLines`, a reason typed in place) or `QuestionDialog` with `inline` (framed, as wide as the pane, `active` while focused; like Claude Code one question at a time: a tab bar `tabBar`/`tabWindow`, ←→/Tab switch, Enter/Space/digit choose and go on, a Submit tab with the answers, a single question sends at once; the body as tall as the tallest tab, at most half the pane inline, the options scrolling with `▲ more`/`▼ more`; text wrapped by `wrapLines`); a request that goes away unanswered by it (`answered` ref) says `already answered in another app` and copies the typed text. Answering (stage 3): a second recording in permission mode default (`test/fixtures/remote-permissions.jsonl`; the user's `defaultMode: "auto"` asked nothing, so the test folder had a `.claude/settings.local.json` with `default`) settled permissions: the worker's `can_use_tool` request carries `tool_name`, `display_name`, `input`, `tool_use_id`, `blocked_path`, `permission_suggestions`; the app allows with `{ behavior: "allow", toolUseID, tool_name, updatedInput: <the input> }` and denies with `{ behavior: "deny", message: "Denied by user", toolUseID }` (`permissionResponse`), and offers no "always allow". `sendResponse` POSTs `{ type: "control_response", uuid, response: { subtype: "success", request_id, response } }`. The list entry names the waiting request in `external_metadata.pending_action` (`request_id`, else `suppressed_request_id`; `tool_name`, `display_tool_name`, `input`, `action_description`), which `parseSession` reads into `RemoteSession.pending` and `SessionSummary.remote.pending`, so Sessions answers without the events; the viewer takes `pendingRequests` of its events first. `useRemoteControl` answers a question with `QuestionDialog` (`questionsOf`, `answersOf`: label or typed text, several joined by ", ", `updatedInput: { ...input, answers }`) and a permission with a `ChoiceDialog` (allow, deny, deny saying why: a `PromptDialog` whose text is the `message`; `toolInputLines` shows the command or file, wrapped through `requestRows`: `wrapLines` and at most 10 rows, `capLines`; `localRequestLines` the same way from `toolInputText`). While an answer window is open, `useRemoteControl` reads the session's events every `TIMING.remotePoll` (the list of Sessions, read every 3 s, kept the request live after the app had answered it), and that or `stillPending` (Sessions: the list's pending request id; viewer: the events) closes the window once another client answered (`already answered in another app`, typed text copied through `onTyped`). Sessions marks a waiting remote session `⚠` (in `SESSION_LEGEND`) and pins it, and `◈` blinks (`SessionMarker` with `color`) while its worker runs. Plans: the app cannot start plan mode remotely, so `ExitPlanMode` was never recorded; it would arrive as a `can_use_tool` too and get the permission window. Still unverified: `refs` matching. Next: SSE (`/events/stream`) instead of polling.

- Session viewers (`src/sessionViewers.ts`, `ViewerTarget`/`openSessionViewer`/`focusSessionViewer`/`viewerCommand` in `open.ts`): `cco watch --session <id>` (or `--remote <id>`) is a viewer of one session, any number per session, each in a new window (`wt -w <viewerWindow()> new-tab`, a random `cco-view-<hex>` name passed back as `--window`; tmux `new-window -n`). There are no roles: whether it has a prompt line depends only on what it shows (remote and `remoteControl`; claude.ai takes several clients, so any number may steer). It replaced the observers (`--observe`, `observers/`) and the one steering remote viewer per session (`remote-<id>.viewer.json`, fixed window `cco-remote-<id>`), whose leftovers the doctor deletes. `cli.ts` registers it (`registerSessionViewer`: `<home>/.claude/cco/viewers/<pid>.json` below the default folder whatever account it reads, from `accountsHome`, with session or remote id, config folder, window, start; removed on exit), not as the project's viewer, and `watch.ts` limits it to the chat and its own settings (`setSessionViewer(true)`, see *Session viewer settings*). `App` treats it as `fixed` (no `p`, `r`, restart, `/cco:…` requests: `useViewerControl` with `control: false`, no view saved per session, `InfoDialog` `oneSession` leaves those keys out); `OneSessionContext` makes `Tabs` draw its two tabs (`1 Chat`, `6 Settings`) and the title after them; there are no roles (observing, controlling) any more. Every one has `SessionComposer` below the chat (`composer`: `fixed` and `isSessionViewer()`), sending through a `PromptChannel`: a remote session's to claude.ai (`sendPrompt`, `sendInterrupt`, `sendResponse`; `blocked` without `remoteControl`), one of this machine's into the Claude Code that runs it (`useLocalPrompt` with `useRunningSession`'s `RunningSession`: `promptSteps` typed by `keysInClaude`, no Ctrl+L, a line break as `\` + Enter, each Enter after a pause; `ESCAPE` while busy; no `select-pane`). `localBlocked` names why it cannot (not running, `kind: bg`, no tmux off Windows, `activity` `waiting`); a blocked line shows that, gives the keys back and leaves `Tab`/`i` to the view switch and the info. On Windows `useLocalPrompt` starts the typer (`prepareConsoleInput`) while the line has the keys and again after each use (`ConsoleTyper.ready`). The console script reads `KeyStep`s as one line of JSON (`stepsLine`, non-ASCII escaped, whatever code page stdin has); `commandSteps` keeps `/resume`'s Ctrl+L. It never exits by itself; `useRunningSession` (the session id in `runningSessions`, every `TIMING.activityPoll`, the `RunningSession` itself, kept while pid, activity and kind stay) gives `liveSession` and the title's status mark, so an unfinished last turn of a session that runs nowhere does not spin. Sessions reads `runningSessionViewers()` every second (`useSessionViewers`), matches them per session (`viewersOf`: the chain's ids and the config folder, or the remote id), draws `◎`/`◎2` (`VIEWED_MARK`, blue, in `SESSION_LEGEND`) and `viewedLine` in the header; `viewerOptions` (`resumeChoice.ts`) adds *Open it in a session viewer* (*Open another session viewer*) for every session after the continue options (for a remote one after the prompt and interrupt) and, while some run, *Bring its session viewer to the front* (the newest with a window); after them `sessionOptions` puts `folder` (*Open its folder*: `openInDefaultApp` on the session's cwd, `SessionSituation.folder`; also for another account's, disabled while `folderMissing`; not for remote ones); `viewer` is the fallback selection before `copy`, and without a terminal it copies `viewerCommand`. The SessionStart hook (`removeStaleSessionViewers`) and the doctor's State files (`staleViewers`, `legacyObservers`, `REMOTE_VIEWER_FILE`) drop registrations of dead pids. The chat's selection is kept per session (`ListPositions.sessions`, `rememberSelection`, `usePositions(cwd, "chat", sessionId)`, falling back to the list's own fields of files written before), and `usePositions` writes only what this viewer changed (`updatePositions` into what is stored then), so a session viewer and the project's viewer keep theirs. Tests point `accountsHome` at a folder of their own (`test/setup.ts`).

Remote Control Viewer (`cco rc-viewer`, `src/rcViewer/`, `src/tui/RcViewerApp.tsx`, `RcViewerView.tsx`): a window that watches the sessions of every project and account (and claude.ai with `remoteApi`). `cli.ts` registers it (`registerRcViewer`, `rc-viewer.json` below `accountsHome`, one per machine: `runningRcViewer` refuses a second; the viewer touches the file every 10 s and one untouched for 45 s counts as gone, since Windows hands the pid of a killed one to other programs) and `runRcViewer` (`watch.ts`) calls `setOwnSettings("rcViewer")`: like a viewer of one session it shows only `SESSION_VIEWS` and keeps `RC_VIEWER_KEYS` in `settings.rc-viewer.json` (`readRcViewerSettings`, the doctor checks it; `isRcViewer()`); the widths `rcViewerSessionsWidth` and `rcViewerTurnsWidth` are only its rows (`RC_VIEWER_ROWS`, listed by `settingsEntries(…, true)` while `isRcViewer()`, with `RC_VIEWER_RESET_ACTIONS`; favourites list `rcViewerSettings`). `RcViewerApp` replaces `App`: two tabs (`RC_VIEWER_TABS` through `TabSetContext`, `1 Remote Control` is mode `chat`), `q`, `i` (`InfoDialog` with `rcViewer`: `RC_VIEWER_INFO_KEYS`, `RC_VIEWER_LEGEND`), F5, its own `ProgressHostProvider`; no update check, no `p`/`r`. `RcViewerView` reads with the hooks of `src/tui/useSessionData.ts` (taken out of `SessionsView`: `useSessions` with all folders, `since` today's midnight and every other account's folder, `useRunning`, `useRemoteSessions`, `mergeRemote`), adds a stand-in (`runningStandIn`) for a running session not read, and `rcViewerEntries` (`src/rcViewer/state.ts`) groups them by `rcViewerState` (`waiting`/`busy`/`idle` from `RunningSession.activity` or the remote `workerStatus`/`pending`, `ended` without a process or connection), keeps since when each is in its state (`SeenStates`) and sorts waiting oldest first, the rest newest first. Its marks blink: waiting `⚠` on and off (`SessionMarker` with `activity="waiting"`, also the Sessions list's `●`/`▶`, a remote session's `⚠` and the Remote Control Viewer row's `⚠n`, through `useBlinkOff`, phase from the clock, the off phase spaces of the same width); a session the Remote Control Viewer saw go from working or waiting to idle (`updateFresh`, `FreshIdle`: not at its start) blinks its `●`/`◈` on and off (`flash`) until selected while the Remote Control Viewer has the focus or `TIMING.freshIdle` (10 min) passed, `TIMING.freshSelected` (3 s) when it was selected in the focused Remote Control Viewer as it finished; `n` (`nextWaiting` with `fresh`) goes to the waiting ones, then to those, the one finished first first. Its list is a `ScreenAside` (`ScreenAsideContext` in `layout.tsx`: `Screen` draws it left of the view's list with its own `AreaContext` and border, shifts the list's and preview's areas, takes its `footer` while it has the keys, else puts `lead` before the view's, `status` before the view's and `focused` for the bar), and the selected session's transcript (`useTranscript`, or `useRemoteTranscript`, which now starts empty for another id) goes to an unchanged `ChatView` with the layout `rcViewerLayout` leaves; `previewKeys` makes `↑↓` scroll in the chat column. The column with the keys (`RcViewerColumn`) decides which list `FocusContext` shows selected, which width `<`/`>`/`|` change (`stepFold`/`toggleFold`) and whether `ChatView` is `active`. Opening it: `openRcViewer(running, select)` (`open.ts`) brings a running Remote Control Viewer to the front (`focusSessionViewer` on its window) after writing `select` (`RcViewerSelect`: id and config folder, or a remote id) to `rc-viewer-request.json` (`requestRcViewerSelect`), which `RcViewerApp` polls (`readRcViewerRequest`, requests newer than its start) and hands to `RcViewerView` as `request` (`matchesRequest`: an id of the chain in that folder); else it starts `cco rc-viewer --config-dir --window cco-rc-viewer` (`RC_VIEWER_WINDOW`) with `--select`/`--select-dir` or `--select-remote` in a new wt or tmux window. Sessions always shows the Remote Control Viewer's row above its list (`RcViewerRow`, outside `List`, which gets the area one row lower: `rcViewerRowLabel` with the waiting count of every account's `useRunning` and the remote list; `useRcViewerRuns`), reached with `↑` from the list's top row (`atListTop`, `rcViewerSelected`: the list's selection shows inactive, Enter opens), a click, or `k`; `rcViewerOption` (*Watch it in the Remote Control Viewer*, last in the Enter dialog, `SessionSituation.rcViewer`) selects the session. `/cco:rc-viewer` runs `cco open --rc-viewer`, which selects the session of its `CLAUDE_PID`. `Enter` in the sessions column opens a `ChoiceDialog` of `rcViewerOptions` (`src/rcViewer/actions.ts`, from a `RcViewerSituation`): `switch` (`switchToSession`; a daemon session has no tab), `prompt`/`answer` (the keys to the prompt line), `interrupt`, `window` (an ended one, `resumeInNewWindow`), the `viewerOptions` and `copy`; selected first: waiting local `switch` (its question is in no file cco reads), waiting remote `answer`, busy `switch` (a slip of Enter stops nothing), idle `prompt`, ended `window`. Below the three columns a `SessionComposer` writes to the selected session (`useLocalPrompt` with the entry's `running`, or a remote `PromptChannel` like `App`'s; an ended local one is blocked with *Enter continues it*), with the pending remote request (`useRemoteTranscript(...).pending[0]`, else the list's); the chat and lists get `shorter(layout, composerRows)` (`layout.tsx`). It is always shown; `Space` (`ChatView` with `spaceMarks={false}` then marks no turn) from any column or a click on its rows gives it the keys, `Tab`/`i` too from the chat column, where `RcViewerView` reports `onClaimKeys` so `RcViewerApp` leaves them alone; a click elsewhere takes them back; while it has them `RcViewerView` reports `onTyping`, its own keys and mouse rest and `ChatView` takes only PgUp/PgDn (`scrollOnly`). `SessionComposer`'s `draftKey` keeps a draft per session (switching loads the other's; a send that ends after a switch clears only its own), and a request of another session is not taken for one answered elsewhere. `useSessionViewers` moved to `useSessionData.ts`. A local session connected to claude.ai (`mergeRemote`'s `twins`: local id → the remote session, from `bridgeIds` or `refs`; only the own account's) keeps its own entry and transcript, but its pending request comes from claude.ai (`useRemoteTranscript(bridge.id).pending[0]`, else the list's), and with `remoteControl` the prompt line's channel is the remote one of that id; `RcViewerSituation.bridge` puts `answer` first for it while it waits. A cyan `⇄` after the marker shows which sessions are answered here (remote ones and `twins`, not ended), dim without `remoteControl`.

- Usage line (setting `usageLine`, on; only session viewers and the Remote Control Viewer): `SessionComposer`'s `usage` goes into the bottom line of its `Frame` (a line above and below every state of the composer, also the inline `QuestionDialog`, open to the sides and without padding; Ink cannot put text into a border, so both lines are drawn as text), at the right: `─── Ctx 62k · 5h 23% 2h14m · 7d 97% 3d4h ──` (`usageParts`, `src/remote/usage.ts`; `fitUsage` shortens it to leave at least two `─` on the left: without the times left, then without `Ctx`, then `5h` alone, else nothing; percentages green, yellow from 50, red from 80; the times left re-read each minute). No percentage for the context: the events name the model but not its window (200k or 1M). `useRemoteTranscript` gives `usage`: `contextOf` (the newest `assistant` event without `parent_tool_use_id` whose `usage` input + cache read + cache creation is above 0; the `<synthetic>` ones are all 0) and the windows of `rateLimitsOf`: the newest `rate_limit_event`'s `rate_limit_info.unifiedWindows.five_hour`/`seven_day` (`utilization` 0–1, `resetsAt` Unix seconds; the recordings have only 1–2 per session), else the window of `rateLimitType`. They are the account's, not the session's, and the newest may lie before the `EVENT_LIMIT` events read, so `keepRateLimits` merges them (`newerLimits`, per window by the event's `created_at`) into `rate-limits.json` in the config folder's `cco` folder, on a report and with each list read (every third poll), which also brings in what other viewers of the account read. A window whose `resetsAt` passed shows `–`. `App` passes it for `remoteId`, `RcViewerView` for a remote session or a `twin` (`remoteRead`). Local sessions get none: their transcripts carry no rate limits.
