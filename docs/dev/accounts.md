# Accounts

Several config folders: finding, showing, continuing in, adding and deleting accounts.

Accounts (`src/account.ts`, `src/tui/useAccount.ts`): `findAccounts` reads `oauthAccount` from `<folder>/.claude.json` of every `~/.claude*` folder and of the viewer's own (`CLAUDE_CONFIG_DIR`); only the default `~/.claude` also falls back to `~/.claude.json` (a custom folder that is not signed in must not show the default account). A folder whose `settings.json` sets `env.ANTHROPIC_BASE_URL` is an API profile instead, whatever login it holds (`readApiProfile`, `Account.api` with `baseUrl` and `ANTHROPIC_MODEL`; `file` is that `settings.json`): `email` holds `apiProfileLabel` (`qwen3.8-27b @ rzisrv051`, the host's first part), so every place that names an account by its email shows it, and the details show server and model instead. `accountInfo(pid)` picks the shown account: the folder whose `sessions/<pid>.json` holds the Claude Code process, else the viewer's own; `multiple` (two or more found); the colour follows the `accountColor` setting alone. `useAccounts` re-reads every 30 s and hands `AccountContext` to `App` and `SettingsView`; `App` gives `AccountBadgeContext` (colour name; none with `accountColor` `off`, shown with one account too) to `Tabs`, which draws the `cco` lead on it, and `AccountAvatarContext` (the account's avatar), which replaces the `cco`, and the avatar as `suffix` to `useTerminalTitle` (`titleWithStatus`: `✳ title · 🦊`, with `accountTitle`, also with one account; the email is no longer in the title). The avatar (`src/avatar.ts`, setting `accountAvatar`, `""` = `cco`) is up to `AVATAR_MAX_WIDTH` (6) columns, measured with `stringWidth`, no control characters (`avatarProblem`; `readSettings` drops any other value, `isAvatarSetting`, which the doctor reports); `avatarLead` draws it as a badge with a space on each side (` 🦊 `, as in the Settings list; `cco` stays as it is), so the tabs move along and `tabAt` takes the avatar to measure it. Like the colour it is chosen per config folder (`Account.avatar`, `chosenAvatarOf`, `avatarOfAccount`: the live setting for the own folder) and `prepareAccount` leaves it out. `AVATAR_PRESETS` are 24 in three groups (ASCII, single emojis, combinations), each with a meaning; their emojis are single code points two columns wide (no VS16, no ZWJ), since joined ones break apart in some terminals. The setting's row has `inline` (its details list each value with its meaning on one line) and `dialog: "avatar"`: `Enter` opens `AvatarDialog` (presets with their meaning, then a `LineField` for one's own, `emojiInputHint` per platform) instead of stepping through `values`. `editLine` and `LineField` step by grapheme (`previousBoundary`/`nextBoundary`, `Intl.Segmenter`), so an emoji is one character. The avatar replaces the colour's name in the account entries' badge (`avatarBadge`) and, in Sessions with other accounts, the `▌` (`accountLead`, all rows padded to the widest avatar, only while one of the accounts listed has one). `ACCOUNT_COLORS` are the console's 16 colours under Ink's names in ANSI order (`black` … `whiteBright`, shown in the terminal theme's colours), each with the text colour readable on it (white on the dark ones, black on the bright ones and `white`). The colour is the FNV-1a hash of the lower-cased email over `AUTO_COLORS` (red, green, yellow, magenta, cyan and their bright ones: no black, white or gray, no blue like the focus bar); the colours before them (`teal`, `amber`, …) are unknown values now and read as `auto`; the `accountColor` setting (`auto`, `off`, or a fixed name; `accountBadge` before it was released, `readSettings` reads its `false` as `off`) is chosen per config folder, in its own settings (`<config folder>/cco/`): the viewer's own folder takes the live setting, every other account the `accountColor` of its folder's `settings.json`, which `readAccount` reads with the account (`Account.chosenColor`, `chosenColorOf`; `hasChosenColor` marks it *chosen* in the details). The Settings view's Account group (after General, always shown) has one info entry per account found (`AccountEntry`, key `account:<dir>`; label `● email (folder)`, the active account `●`, the others `○`, its avatar, else its colour name, at the right end as a badge on its colour, like the value list (`look`) and the details (`colorBadge`); `account:none` while there is none), then its three settings (`accountColor`, `accountAvatar`, `accountTitle`), then `account:details` (how they were found); built in `settingsEntries(update, accounts)`.

Continuing in another account (`src/accountContinue.ts`, `src/export/toAccount.ts`, `src/accountSetup.ts`, `src/transfers.ts`): every path goes through `claudeDir()`, so a viewer sees only its own config folder; `inClaudeDir(dir, fn)` (`locate.ts`) runs synchronous code as if `CLAUDE_CONFIG_DIR` were another account's folder, and `withClaudeDir(env, dir)` gives a child process that folder (the default `~/.claude` removes the variable, since only it falls back to `~/.claude.json`). The Enter dialog's `account` option (only with another account found, `SessionSituation.accounts`; `/cco:account [query]` is `cco open --view sessions --action account --select <query>`, `matchAccount`, which `App` hands to Sessions as `accountRequest`) asks for the account (`otherAccounts`), then confirms (`askHow`, a `ConfirmDialog`); the session where it is, running or not, and the viewer stay as they are. `continueInAccount` runs `pluginSteps` (marketplace add from this account's `known_marketplaces.json` source, install or enable, through `runInAccount` = `runCommandWith(withClaudeDir(…))`) and stops before anything else if they fail (`plugin-failed`; `Esc` on the failed dialog offers to go on with `skipPlugin`), then `prepareAccount` (copies `cli.json` and, if missing, `settings.json` without `accountColor` and `accountAvatar`), and `copyToAccount`: `backupFiles` of the chain written below the other folder with `relocatedData` (`claudeFrom`/`claudeTo`, same cwd and slug), new UUIDs when any id of the chain is in that folder already, `mergeCcoData` there; then `recordTransfer` writes `<slug>.accounts.json` on both sides (`to` list, `from`), which Sessions shows as `⇢`/`⇠` and `transferLines` in the header. The copy then starts in a new window under that folder (`startThere`: `resumeInNewWindow` with `configDir`; wt: `cco claude --config-dir <dir> -- --resume <id>`; tmux: `export CLAUDE_CONFIG_DIR=…` in the window's command; without a terminal the progress dialog shows the command), whose SessionStart hook opens a viewer there as that account's `autoOpen` says; there is no pairing across accounts. The `ChoiceDialog` is keyed by its title, since one dialog follows another.

Accounts view (`src/tui/AccountsView.tsx`, `src/accountsInfo.ts`; its trash: see *Deleting an account* below): `Mode` `accounts`, key `0`, no tab: `tabAt` gives it for the "cco" lead (`TABS_LEAD`), which `Tabs` shows `inverse` while it is open; first in `TAB_ORDER` (so `←`/`→` pass it), shown while `viewAccounts` is on (`isViewShown`, not in `VIEW_SETTINGS`, so it is not a tab for `isLastView`; off, `tabAt` gives nothing for the "cco" and `0` does nothing, an explicit `--view accounts` still opens it), never `shownView`'s stand-in. `accountEntries`: the active account, the others in the `accountsOrder` (`email`, `folder`, `recent` by `accountUsedAt`: the mtime of `history.jsonl`, else of `.claude.json`; `s` goes round), `details` (Settings' `accountLines`), or `none`. Details: `accountPlugin` (`pluginState`, `knownMarketplaceSource`), `accountRunning` (`runningSessions` in that folder, which now also keeps `cwd`) every 3 s while shown, `accountSessions` (the project's transcripts with a conversation, the newest's title from its last 128 KB via `transcriptTitle`, the `<slug>.accounts.json` counts) with the account list and on F5. Marks are a global favourites list (`accounts`, next to `settings` in `favorites.json`, keyed by folder); positions list `accounts`; width `accountsListWidth`. `Enter` (and in Settings `Enter` on an account entry) opens `useAccountFlow`'s `accountMenu`: `continue` (greyed out on the active account and without `sessionPath`, `noSession` naming why; `App`'s `continuable`: a `claudePid`, no `--session`, a transcript), `new` (`startNew`: `continueInAccount` without a session only runs the plugin steps and `prepareAccount`, then `startThere` with `fresh`, a `randomUUID` passed as `claude --session-id`; its hook opens its own viewer, this one stays), `folder` (`openInDefaultApp`). `useAccountFlow` (`src/tui/useAccountFlow.tsx`) holds the whole flow taken out of `SessionsView`: the account choice (`askAccount`), `askHow`, `runContinue`, the plugin failure's question (`pluginFailed`), the pairing wait (`startPairing`, `pairingProgress`, for Sessions' `window-attach`) with its own dialogs (`element`) and progress; `ownSession(path, cwd)` reads the viewer's session (`SessionReader` plus `predecessors`) for it.

- Other accounts in Sessions: with another account checked in the filter, `useSessions` keeps one `SessionIndex` per config folder (`new SessionIndex(dir)` reads that folder through `inClaudeDir` and sets `SessionSummary.account` on its sessions) and merges them by `lastActive`; `useRunning` reads every folder's `runningSessions`. Entries, marks, positions and the running map are keyed by `sessionKey` (`<folder>|<id>` for another account's, since a copy may keep its id); `isActive` never matches another account's. Each row starts with a bar in `barColorOfAccount` (`account.ts`: the account's colour, `gray` for `off`), the header gets `sessionAccountLines` (email, organisation, folder, `pluginState`). `Enter` on one opens the same dialog as for this account's (`SessionSituation.foreign`: `sessionOptions` greys out what works on this folder only with `OWN_ONLY`, leaving `switch`, `window` (`resumeInNewWindow` with its folder) and `copy` (`resumeShellCommand`, which writes a folder in the home folder as `%USERPROFILE%\…` or `"$HOME/…"`)); `d` says `only for sessions of this account`, the export leaves them out, the trash stays this account's.
- Adding an account (`src/addAccount.ts`, `AddAccountDialog`, `useAccountFlow.askAddAccount`): the entry *how to add an account* (`AccountEntry` `add` in Settings, kind `add` in the Accounts view; preview `addAccountLines`). The dialog asks command and folder (`FOLDER_PATTERN` `.claude-<name>`, so `findAccounts` finds it); `checkNewAccount` refuses PowerShell aliases (`powershellAliases`: `Get-Alias` from powershell.exe and pwsh with the profile, through `proc.execFile`; without an answer `POWERSHELL_ALIASES`), `CMD_BUILTINS`, `BASH_BUILTINS`, a program of that name on the PATH outside the scripts' folder (`commandOnPath`, with PATHEXT), an existing script and a signed-in folder, and offers an empty folder again (`reuse`). `writeAccountFiles` writes `startScripts` into `claudeBinDir()` (the PATH folder holding claude, else `~/.local/bin`): `<cmd>.cmd` (CRLF, `setlocal`, `set "CLAUDE_CONFIG_DIR=%USERPROFILE%\…"`, `call claude %*`) and a Bash script (`$USERPROFILE\…` on Windows, since Git Bash hands the value to claude.exe unchanged; `$HOME/…` elsewhere, chmod 755), `wx` so nothing is overwritten; then `continueInAccount` without a session (plugin, `prepareAccount`) and `scriptInNewWindow` (`wt … cmd /k <script>`, tmux `<script>; exec $SHELL`). The home folder comes from `accountsHome.get()`: tests swap it, since `os.homedir()` ignores a changed `USERPROFILE` on Windows and a test once created a folder in the real home.
- Deleting an account (`src/accountTrash.ts`, `TypedConfirmDialog`, `useAccountFlow.askTrash`/`askPurge`/`askEmpty`/`restore`/`undoTrash`): `d` (Accounts view, Settings' account entries) or the account menu's last option (`ChoiceOption.danger`: red, below a `── Danger zone ──` line that `ChoiceDialog` counts in its height). `accountDeleteBlocker` refuses `~/.claude`, the active account, one with a live `sessions/<pid>.json` (`runningSessions` through `inClaudeDir`) or a live viewer registration in its `cco/` (`accountViewers`); a `ConfirmDialog` (danger) shows `accountTrashPlan` (scripts, size, sessions), then `TypedConfirmDialog` wants the folder name (`delete` for emptying). `trashAccount` writes `manifest.json` first, renames the folder into `accountTrashRoot()` (`~/.claude/cco/trash/accounts/<folder>-<ms>/folder`, from `accountsHome`, so every viewer sees one trash), with no copy fallback: on Windows the rename fails while a process holds a file there (`EBUSY`/`EPERM`), and the entry is removed again; then the start scripts (`startScriptsOf`: files of up to 4 KB in `claudeBinDir()` and `~/.local/bin` whose `CLAUDE_CONFIG_DIR=` resolves to the folder, `scriptFolder`). `restoreAccount` refuses while a place exists again; `purgeAccount` also drops the `accounts` mark. The Accounts view's `T` lists `listAccountTrash()` (entries `kind: "trashed"`, the filter off, `Esc` leaves it), `u`/`x`/`X` as in the Sessions trash; `AccountState.refresh` reads the accounts again after a change.
